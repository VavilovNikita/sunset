# Static audit — sunset (backend) + sunset-beach (frontend)

Date: 2026-10-03. Branch audited: `claude/happy-gates-yn3b2t` in both repos (backend HEAD `d9267f8`, frontend HEAD `17e36de`).

## Scope and method

- Read `CLAUDE.md` in both repos, `DEPLOY.md`/`README.md` (frontend), `backup/*.md` (backend), and `openapi.yaml`. **There is no `DEPLOY.md`, `HANDOFF.md` or `feature_backlog_from_innkeeper.md` in either repo**, so I could not check settled or deferred decisions against them. Where `CLAUDE.md` documents a decision, I did not re-argue it.
- Static reading of every backend package (security, controllers, all services, migrations V1–V129, config, Docker/compose, backup scripts) and of the frontend's proxies, middleware, session handling, `lib/`, and the POS, booking, spa and guest flows.
- Scripted cross-checks:
  - All 213 `openapi.yaml` operations against the controller mappings: complete in both directions.
  - All frontend API path literals against the spec.
  - 174 hand-mirrored frontend types against the spec schemas: field names and nullability.
  - Unused exports and methods in both repos.
  - Git history in both repos for committed secrets: none found apart from test-only JWT secrets.
- **What did not run:** neither test suite. Installing the frontend dependencies and the Maven/Testcontainers stack needs network access, which this pass was told not to use. Nothing was tested in a browser either. Findings that depend on runtime behaviour say so.
- Test counts as they actually are: the backend has 124 test classes and 1,117 `@Test` methods. The frontend has 41 test files and 358 test cases. The numbers in the brief (≈358 backend / ≈110 frontend) look swapped or stale.

Severity key: **Critical** = data loss, security hole, or production-breaking. **High** = a real bug likely to bite, or a meaningful contract mismatch. **Medium** = dead code, duplication, or a real code path without tests. **Low** = consistency nits and documentation drift.

## Critical

### C1. `V1_1__prisma_baseline_schema.sql` will probably fail Flyway validation on the production database
- **Where:** `sunset/src/main/resources/db/migration/V1_1__prisma_baseline_schema.sql` (added in `8726ab6`, 2026-09-22); `application.properties` (`spring.flyway.baseline-on-migrate=true`, `baseline-version=1`); `src/test/resources/test-db-baseline.sql` lines 2152–2153.
- **Failure scenario:** Production adopted the old Prisma schema through `baseline-on-migrate`. Its `flyway_schema_history` therefore holds a `BASELINE` row at version 1, followed by V2…Vn. V1_1 sorts as version 1.1: above the baseline but below migrations already applied. Flyway classifies such a migration as *ignored*. With the defaults (`validateOnMigrate=true`, `ignoreMigrationPatterns=*:future`, `outOfOrder=false`), startup fails with "Detected resolved migration not applied to database: 1.1" and the backend does not boot. If someone "fixes" this with `outOfOrder=true`, V1_1 runs `CREATE TYPE "Role"` against the live schema and fails anyway.
- **Why the tests don't catch it:** The committed test baseline was regenerated from an empty database. Its history has V1 as an ordinary `SQL` row and V1_1 as applied, so the suite never models production's history.
- **Open question (answer first):** Has any backend deploy since 2026-09-22 actually started on the VPS? What does `SELECT installed_rank, version, type FROM flyway_schema_history ORDER BY 1 LIMIT 5` return in production? If deploys have succeeded, someone patched the history or the config by hand, and that needs writing down. If not, every further backend deploy, including the SiteMinder one, is blocked.
- **Fix direction:** Keep the fresh-database bootstrap without a versioned migration under the baseline. Options:
  - Make the fresh-DB path a Flyway callback, or a `baselineMigrate`-aware script that only runs on an empty schema.
  - Or add `ignoreMigrationPatterns=*:ignored` scoped to 1.1, with a documented reason.

  Add a test that starts from a production-shaped history (a BASELINE row at 1) and runs `migrate`.

### C2. Postgres may be reachable from the internet with the default password (verify on the VPS)
- **Where:** `sunset-beach/docker-compose.yml` lines 9–14 (`POSTGRES_PASSWORD: sunsetbeach`, `ports: "5434:5432"`, no host binding). `sunset/backup/pg_backup.env.example` and `pg_backup.sh:20` default `PG_CONTAINER=sunset-beach-db-1`, i.e. that container. `sunset/backup/RESTORE_RUNBOOK.md:97` (`-p 5434:5432`). `sunset/.env.example` "Scenario B". `sunset-beach/DEPLOY.md` step 0 (relies on `ufw`).
- **Failure scenario:** The backup tooling's defaults suggest production Postgres is the `db` service from sunset-beach's dev compose file. That file publishes 5434 on all interfaces with a hard-coded password. Docker writes its own iptables rules, which bypass `ufw`, so "only 22 and 8888 are open" may not hold. Anyone who finds port 5434 can log in as `sunsetbeach/sunsetbeach` and read or destroy every guest, booking and payment record. The restore runbook repeats the exposure: after a restore, the database comes up on `0.0.0.0:5434`.
- **Open question:** On the VPS, run `docker ps --format '{{.Names}} {{.Ports}}'` and `ss -ltnp | grep 5434`, and check the real `POSTGRES_PASSWORD`. If this does not apply, the finding drops to Low (risky defaults in docs).
- **Fix direction:** Bind to `127.0.0.1:5434:5432` (or publish no port and use a shared Docker network). Move the password into an env file that is not committed. Fix the same binding in the restore runbook. Give production Postgres its own compose project, separate from the frontend's dev file.

## High

### H1. A self-registered guest JWT passes every staff route guarded only by `authenticated()`
- **Where:** `sunset/.../security/GuestJwtAuthFilter.java` (honoured on every path, grants `ROLE_GUEST`). `SecurityConfig.java` lines 65, 136–137, 158, 220, 235, 244, 248, 354, 403 and 409 (`anyRequest().authenticated()`).
- **Failure scenario:** Anyone can register a guest account on the public site, verify it, and log in. With that token:
  - They can read the folio total, room-charge orders and folio payments of **any booking whose id they know**: `GET /bookings/{id}/folio`, `/pos-orders`, `/folio-payments`.
  - They can read the full menu (including unavailable and spa items), `/tables`, `/restaurant-map` and `/shift-codes`.
  - Calls to `GET /maintenance-tasks`, `POST /maintenance-tasks`, `GET /roster/me`, `GET /auth/me` and `PATCH /auth/password` hit a `(StaffPrincipal)` cast and return a raw 500. `CurrentUser`, `MaintenanceTaskController:36/49`, `RosterController:288` and `AuthController:104` all cast.

  `CrossIdentityTokenRejectionTests` only checks `/users`, which is role-gated, so the gap is untested.
- **Fix direction:** Replace `authenticated()` on staff routes with `hasRole(WAITER)` (the bottom of the staff hierarchy). Make `anyRequest()` require a staff role as well. Optionally scope `GuestJwtAuthFilter` to `/guest/**`, the same way `IntegrationKeyAuthFilter` is path-scoped. Extend the cross-identity test to every `authenticated()` matcher.

### H2. Rate limiting is keyed on a client-controlled `X-Forwarded-For`, while every request proxied through Next.js shares one IP
- **Where:** `sunset/.../security/ClientIpResolver.java:18` (trusts the first XFF hop). `sunset-beach/nginx/conf.d/app.conf:43,55,68` (`$proxy_add_x_forwarded_for` *appends* to whatever the client sent). Callers: `AuthController.login`, `GuestAccountAuthController` (register/verify/resend/login/unsubscribe), `BookingController` (public `POST /bookings`). On the frontend, `app/api/session/login`, `app/api/guest-session/*` and `app/api/public-proxy` call the backend server-to-server without forwarding any client address.
- **Failure scenarios:**
  1. **Public bookings are capped at 8 per hour for the whole site.** The booking form posts through `/api/public-proxy/bookings`, so the backend sees the Next.js container as the only client. `BookingRateLimiter` allows 8 attempts per IP per hour, counting failures too. The ninth guest in an hour gets "Too many booking requests from this address". The same collapse caps guest register/verify/resend/unsubscribe at 20 per 15 minutes site-wide. Staff login failures through the UI are counted per email on the shared IP, so five wrong guesses at a known staff email lock that person out of the UI for 15 minutes.
  2. **Brute force and email relay through direct calls.** `/api/auth/login` and `/api/guest-auth/*` are reachable directly through nginx. Rotating a fake `X-Forwarded-For` gives a fresh bucket on every request: unlimited password guessing against staff accounts, and unlimited verification emails to arbitrary addresses (see H4).
- The limiter maps (`attemptsByIp` and friends) never evict keys, so rotating XFF values also grows memory without bound.
- **Fix direction:** Trust a client address only from a known proxy. In nginx, set `X-Real-IP $remote_addr`, or overwrite XFF with `$remote_addr`, and read that. In the Next.js routes, forward the incoming client IP as a header the backend trusts only from the BFF. Add a global per-account failure limit independent of IP. Evict stale buckets.

### H3. Guest account pre-hijacking: re-registering a pending email keeps the first registrant's password
- **Where:** `sunset/.../service/GuestAccountService.java:64–90` (`register`), and `verify`.
- **Failure scenario:**
  1. The attacker registers `victim@example.com` with a password of their choosing.
  2. The victim later registers with the same email. The code finds the unverified account, regenerates the token and re-sends the email, but keeps the attacker's password hash.
  3. The victim clicks the link and the account is verified.
  4. The attacker can now log in as the victim. They see the victim's bookings, and while the victim is checked in, can place room-service orders against the victim's booking (`GuestOrderController`). The victim cannot log in with their own password.

  The same applies if the victim never registered and simply clicks a verification email they didn't ask for.
- **Fix direction:** On re-register of an unverified account, overwrite the password hash (and name) with the latest request's. Or collect the password at verification time instead of at registration. Bump `tokenVersion` on verify.

### H4. HTML injection in outgoing email, including to arbitrary addresses
- **Where:** `sunset/.../service/EmailService.java`:
  - `sendNewBookingEmail` (55–82): guest name, email and phone from the unauthenticated booking form go into the staff email.
  - `sendBookingExpiringReminderDigestEmail` (105–145).
  - `sendGuestStatusEmail` (153–175).
  - `sendGuestVerificationEmail` (216–223): `name` comes from the unauthenticated register call, and the recipient is any address.

  The lifecycle emails escape with `HtmlUtils.htmlEscape`/`escapeName`; these four do not.
- **Failure scenario:** An attacker registers a guest account for any address with `name` set to `<a href="https://evil/…">Confirm your booking</a>`. The hotel's own Resend domain delivers that phishing content. Combined with H2, the per-IP limit can be bypassed, leaving only the 5-per-hour-per-address cap, so this works as an open relay that can get the sending domain suspended. A booking with an HTML guest name similarly injects links into the email managers receive.
- **Fix direction:** Escape every interpolated value through one helper (the lifecycle emails already do), and add a test that feeds `<` and `"` through each template.

### H5. Lost updates on `Order` and `Booking`: no row lock or version on most writes, and Hibernate writes whole rows
- **Where:** No entity has `@Version` or `@DynamicUpdate`, so every UPDATE writes every column from the snapshot that was loaded. Locks exist only in `OrderService.close`/`voidItem` and `BookingService.updateStatus` (`findByIdForUpdate`). Unlocked writers include:
  - `OrderService.addItems` (371), `update` (338), `updateItem`, `deleteItem`, `cancel` (650).
  - `BookingOccupancyService.checkIn` (98), `checkOut`, `markNoShow`.
  - `BookingService.assignGuest`.
  - `BookingExpiryService.sweepUnconfirmedPublicBookings` (112–148).
  - `SiteMinderImportService.recordLastChangedAt`.
- **Failure scenarios (real races, not theory):**
  - A waiter (or a guest via QR, `addGuestItems`) adds a line while the cashier closes the order. `close` locks the row, records the payment and posts to the ledger, then commits. `addItems` had already read the order as `SENT`. Its UPDATE waits on the lock, then writes `status='SENT', total=<new>` over `PAID`. The result: an order back to unpaid, with a payment and ledger entry for the old total and an extra line nobody paid for. `cancel` racing `close` can overwrite `PAID` with `CANCELLED` after the money was posted.
  - Reception checks a guest in while a cashier marks the booking `PAID`. `updateStatus` posts the room settlement to the ledger. `checkIn`'s stale UPDATE then writes `status=CONFIRMED` back, so the ledger shows a settlement for a booking that is not PAID. The next "mark PAID" posts a second settlement, doubling room revenue in Z120.
  - The expiry sweep can overwrite a booking that staff confirmed a moment earlier back to `CANCELLED`.
- **Fix direction:** Add `@Version` to `OrderEntity` and `BookingEntity` and map the optimistic-lock failure to a 409. Or take `findByIdForUpdate` in every writer of those two tables. Add `CyclicBarrier` race tests for addItems-vs-close, cancel-vs-close and checkIn-vs-updateStatus, matching the existing `OrderDoubleCloseRaceTests`.

### H6. A cancelled booking can be reinstated, or checked in, without an availability check
- **Where:** `BookingService.updateStatus` (301–356) accepts any status → any status. `BookingOccupancyService.checkIn` (98–118) never looks at `status`. On the frontend, `components/admin/BookingStatusForm.tsx:15` and the calendar panel offer all four statuses for a cancelled booking; `lib/bookingStatusChange.ts` only guards moving *into* CANCELLED.
- **Failure scenario:** Booking A for room 5 (10–12 Oct) is cancelled, and the room is resold to booking B. A guest calls back and staff switch A to `CONFIRMED` or `PAID`. A's segments still point at room 5, so the room is now double-booked and availability goes negative. If PAID, a settlement is posted too. Separately, a cancelled booking can be checked in, putting a guest in a room another booking holds. SiteMinder deliberately refuses to reinstate cancelled bookings, but the staff path has no equivalent rule.
- **Fix direction:** Leaving `CANCELLED` should either be forbidden (409, with a message to create a new booking) or go through `BookingWriter`'s SERIALIZABLE availability check for the existing segments. Reject (or at least warn about) check-in of a `CANCELLED` booking. Remove the reinstating options from the status dropdown.

### H7. Any cashier can close another cashier's shift, and the closer is recorded as the opener
- **Where:** `sunset/.../controller/ShiftController.closeShift` → `ShiftService.close(id, input)` (142–163). Line 154 sets `closedByUserId = openedByUserId`.
- **Failure scenario:** The service hides other cashiers' shifts from `getSummary` with a 404, but `close` has no ownership check at all. Cashier B, or a manager tidying a forgotten shift, can close A's drawer and type in a counted-cash figure. The shift record, the Z report and `GET /shifts` then name **A** as the person who counted, so a discrepancy is pinned on the wrong person. Only the audit-log actor is correct. There is also no lock: an order closed at the same moment can attach its payment to a shift whose Z report has already printed.
- **Fix direction:** Pass the caller into `close`. Allow it for the opener; for MANAGER+ allow it but record the real closer. Lock the shift row (`FOR UPDATE`) in both `close` and `OrderService.close`'s shift lookup.

### H8. The spa auto-link by table compares a UTC timestamp with Bangkok slot times
- **Where:** `sunset/.../service/OrderService.java:298–330` (`resolveByTable`, `resolveByBooking`). These are fed `Order.createdAt`, an `@CreationTimestamp`. `ClockConfig`'s own javadoc confirms the JVM runs in UTC in production.
- **Failure scenario:** An order opened at 15:00 Bangkok is stored as `createdAt = 08:00` (UTC wall clock). `isDuring` and `isWithinGraceOfEnding` compare 08:00 against appointment start times held in Bangkok time. The 14:00–15:00 treatment never matches, and an unlinked 08:00 appointment on the same table would be linked wrongly. The by-booking axis uses `createdAt.toLocalDate()` (the UTC date), which is wrong between 00:00 and 07:00. The result: `missingTreatmentNames` stays non-empty for treatments that were billed, or goes quiet on the wrong appointment.
- **Why tests pass:** `OrderSpaAppointmentLinkTests` back-dates `createdAt` to the *same local wall clock* as the appointment (lines 256–296), which hides the offset. Lines 304 and 324 also read `LocalDateTime.now()`, against the CLAUDE.md test rule.
- **Fix direction:** Convert `createdAt` with `TimestampFormat.toUtc(createdAt).atZoneSameInstant(clock.getZone())` before comparing, as `RevenueExportService.localDateTime` does. Fix the test to store a genuine UTC `createdAt`.

### H9. Date filters on UTC timestamps use UTC days, so they disagree with the reports
- **Where:**
  - `PaymentService.getSummary:31–33` (`GET /payments/summary`).
  - `OrderService.buildSpecification:859–875` (order history, including the "closed" basis).
  - `AuditLogService.search:233–236`.
  - `ShiftService` list (377–384, `openedAt`).

  By contrast, `/reports/*` and `RevenueExportService` correctly use `ReportDateRange.startUtc(clock.getZone())`.
- **Failure scenario:** A bar tab paid at 01:30 Bangkok on 3 Oct is stored as 18:30 UTC on 2 Oct. `/payments/summary?from=2026-10-03&to=2026-10-03` leaves it out (it lands under 2 Oct), while Z410 and the revenue export put it under 3 Oct. The same goes for "orders closed on…", "audit log for…" and "shifts opened on…". Totals for the same day differ between screens for anything between 00:00 and 07:00 Bangkok. `PaymentService` also lets `DateTimeParseException` escape as a 500.
- **Fix direction:** Route all of these through `ReportDateRange` (or an equivalent shared helper) and add a test with a 01:30-Bangkok payment.

### H10. SiteMinder re-polls silently revert staff edits (blocks the SiteMinder go-live)
- **Where:** `sunset/.../service/SiteMinderImportService.java:109–137` (the stale check uses strict `isBefore`, line 122) and `update()`.
- **Failure scenario:** The polling script re-posts every reservation on every poll. A re-post of an *unchanged* SiteMinder version (`lastChangedAt == externalModifiedAt`) passes the stale check, so `update()` re-diffs and "applies whatever differs". If front desk extends a SiteMinder guest by a night, corrects the party size, or reprices the booking, the next poll quietly reverts it, attributed to `SITEMINDER`. That includes `updateSchedule` shortening the stay back and dropping the extra night's agreed rate. Nothing in `SiteMinderImportServiceTests` covers "staff edit, then same-version re-poll".
- **Fix direction:** Only apply a SiteMinder version newer than the last one applied. To keep "a partial failure converges on the next poll", record whether the last apply completed (for example, write `externalModifiedAt` only after every step succeeded, and have an equal timestamp mean "done"). Decide explicitly, and write down, what wins when staff and SiteMinder disagree. Consider whether an OTA cancellation of a `CHECKED_IN` booking should warn instead of cancelling.

### H11. The committed deploy config does not describe production; redeploying from the repo would break the site
- **Where:** `sunset-beach/nginx/conf.d/app.conf`; `sunset-beach/DEPLOY.md`; `sunset-beach/.env.production.example`; `sunset-beach/CLAUDE.md` ("COOKIE_SECURE"); `sunset/docker-compose.yml:16`.
- **Failure scenarios:**
  - nginx carves out only `/api/session/` for Next.js. Every other `/api/*` goes to the backend, including `/api/admin-proxy/*`, `/api/guest-proxy/*`, `/api/public-proxy/*` and `/api/guest-session/*`, which are Next.js routes. Installed as committed, every admin client call, the public booking form, QR ordering and guest login would all return 404s from Spring.
  - DEPLOY.md and the nginx file describe plain HTTP on `thesunsetbeachsip.ddns.net:8888` with `COOKIE_SECURE=false`. `.env.production.example` and CLAUDE.md say production is HTTPS on `sunsetsamui.com` with `COOKIE_SECURE=true`.
  - The backend compose file publishes `127.0.0.1:8080`, while the nginx config and DEPLOY.md proxy to `8082`.
  - DEPLOY.md assumes `/opt/sunset`; the brief says `/root/sunset/sunset/.env`.
  - The backend repo has no deploy doc at all.
- **Fix direction:** Commit the nginx config actually running in production, or document where it lives. Make one doc authoritative for host, TLS and ports. Keep VPS-local compose changes in an override file rather than in uncommitted edits.

## Medium

### M1. Printing joins the business transaction
- **Where:** `PrintService.queueAndAttempt` (52; `@Transactional` REQUIRED) and `retryPendingJobs` (121–134; a single transaction around every network send).
- **Scenario:**
  - The socket send runs inside the order or shift transaction while row locks are held (`close` holds `FOR UPDATE`): up to 2 s of connect timeout per printer, plus an unbounded write against a wedged printer.
  - A guest receipt can print for a `close` that then rolls back.
  - If `saveAndFlush` of the job fails, the interceptor marks the caller's transaction rollback-only. `OrderPrintingService`'s catch cannot save it, so the close fails with `UnexpectedRollbackException`. That breaks "printing never breaks the operation".
  - The background sweep and a manual retry of the same PENDING job can both send it, producing a double print.
- **Fix direction:**
  - Persist the job in the caller's transaction, but send only after commit (`TransactionSynchronization.afterCommit`) or on a separate thread.
  - Use `REQUIRES_NEW` for the status update.
  - Give each sweep item its own transaction, and claim jobs with `FOR UPDATE SKIP LOCKED`.

### M2. The audit log isn't really fail-open, and it can record operations that never happened
- **Where:** `AuditLogService.record` (126–145).
- **Scenario:**
  - `persist` calls `save()` without a flush, so the INSERT runs when the `REQUIRES_NEW` transaction commits, after the try/catch. A failing insert therefore propagates into the business call. A likely trigger is an `AuditAction` value added in Java without its `ALTER TYPE` migration; the history from V92 to V129 shows how often new values arrive.
  - Because audit commits first, an operation whose own commit later fails keeps an audit row claiming it succeeded.
- **Fix direction:**
  - Use `saveAndFlush` inside the try.
  - Ideally, write audit rows after commit; keep `REQUIRES_NEW` only where the current semantics are relied on.
  - Add a startup check that every `AuditAction`/`AuditEntityType` value exists in the Postgres enum.

### M3. Bare wall-clock reads (`LocalDate.now()`, `LocalDateTime.now()`) that ignore the shared `Clock`, against the CLAUDE.md rule
- **Where:**
  - Real "today" bugs (7 h off between 00:00 and 07:00 Bangkok):
    - `BookingWriter.previewReprice:994`: a reprice at 02:00 Bangkok can reprice *last night*, against the "today forward" rule.
    - `RoomUnitService:254` and `UserService:408`: "has future bookings/appointments" checks.
    - `MaintenanceTaskService:254`: block end date.
    - `RosterExportService:149`.
    - `RosterGridImportService:269`: `effectiveFrom` of a shift code created during import.
    - `BookingExpiryService:120`: business days counted on UTC dates.
  - Visible output: every kitchen/bar ticket, void ticket, pre-bill and test print shows `Time: … UTC`. See `OrderPrintingService:126,215,246` and `PrinterService:270`.
  - Correct only while the JVM stays on UTC: `OrderService:677` (`sentAt`), `ShiftService:155`, `MaintenanceTaskService:212`, `PrinterService:189`, `AttendanceDevicePollService:213,238`, `GuestAccountService:88,104,113,116`.
- **Fix direction:**
  - Inject `Clock` everywhere.
  - Print ticket times in hotel time.
  - Add a CI grep, or an ArchUnit rule, banning argument-less `now()` in `src/main`.

### M4. Double-submitting a folio payment posts cash twice
- **Where:** `BookingService.recordFolioPayment` (949–982).
- **Scenario:** The booking row isn't locked. Two quick submits both read the same outstanding amount, both pass the overpay check, and both post Dr Cash / Cr Guest Ledger. The folio floors at zero, so the screen looks fine while the ledger and the cash report are overstated.
- **Fix direction:** `findByIdForUpdate(bookingId)` before computing the outstanding amount. Optionally add an idempotency key from the client.

### M5. Spa appointments: no row lock on edits, and incomplete server-side validation
- **Where:** `SpaAppointmentService.addTreatment` (279), `removeTreatment` (317), `updateStatus`, `updateSchedule` (386); `create` (222).
- **Scenario:**
  - Two concurrent `removeTreatment` calls on a two-treatment appointment both pass the "at least one" check, leaving zero treatments.
  - A concurrent add and remove lose an update on `durationMinutes`, so the exclusion constraints guard the wrong interval.
  - `create` and `updateSchedule` accept a table outside the SPA zone or an inactive one, and an inactive user or one without the THERAPIST function. `getSchedule` lists only active SPA tables, so such an appointment is invisible on the grid while it still blocks its slot.
- **Fix direction:** Lock the appointment `FOR UPDATE` in every mutator, and validate zone/active/function on the server.

### M6. QR and room-service ordering don't validate what is ordered
- **Where:** `OrderService.addItems` (used by `addGuestItems` and `RoomServiceOrderingService`); `openapi.yaml` `OrderItemInput` (no maximum quantity) and the array bodies (no `maxItems`).
- **Scenario:**
  - A guest on a stale menu page orders an item that was just marked unavailable, and the kitchen gets a ticket for a sold-out dish.
  - A known spa item id can be ordered from a restaurant QR code.
  - A prankster holding a table's QR code can add `quantity: 99999` (an int merge can even overflow), and the ticket prints. The per-token limiter only caps the request count.
- **Fix direction:** On the guest paths, reject `isAvailable=false` and `SPA`-department items. Add sane `maximum`/`maxItems` to the spec.

### M7. The spec says guest email and phone are non-null strings, but the backend returns null
- **Where:** `openapi.yaml` `Booking.required` includes `guestEmail`/`guestPhone` (type string, not nullable). V17 dropped `NOT NULL`. Staff walk-ins and **every SiteMinder import** (`BookingWriter.insertExternal` passes `null, null`) return `null`.
- **Scenario:** The frontend's `lib/types.ts` declares `guestEmail: string`. Screens survive only because they happen to use truthiness checks (`GuestLinkEditor`, `BookingCardPanel`). Any new code calling `.trim()` or `.toLowerCase()` on it, or any other consumer built from the spec, will crash on SiteMinder bookings.
- **Fix direction:** Mark both `nullable: true` in the spec, update the frontend type to `string | null`, and let the typecheck surface the call sites.

### M8. CSV exports can execute formulas
- **Where:** `CsvBuilder.escape` (44–52), used by `GET /bookings/export` and `GET /shifts/{id}/export`.
- **Scenario:** A public booking with guest name `=HYPERLINK("http://evil","Open")` (or a DDE payload) runs when a manager opens the export in Excel.
- **Fix direction:** Prefix values that start with `= + - @ \t \r` with `'`. The `.xlsx` exports via POI `setCellValue(String)` are safe.

### M9. Error shapes leak or diverge
- **Where:** `GlobalExceptionHandler` has no handler for `DateTimeParseException`, `ClassCastException`, `HttpMessageNotReadableException`, `MethodArgumentTypeMismatchException`, `ArithmeticException` or plain `RuntimeException`.
- **Scenario:**
  - Pattern-valid but impossible dates (`2026-02-30`) produce 500s instead of the documented 400 `ValidationError` in at least: `POST /bookings`, `/bookings/staff`, `/bookings/staff/quote`, `/integrations/siteminder/reservations`, `/spa-appointments`, `/payments/summary` and the audit-log filter.
  - Malformed JSON gets Spring's default error body, which has a different shape.
  - H1's guest-token 500s come from the same gap.
- **Fix direction:** Map these to the existing `ValidationError`/`ErrorMessage` shapes, and parse dates through one helper (`ReportDateRange.parseDate` already exists).

### M10. Uploaded files are not backed up
- **Where:** `sunset/backup/pg_backup.sh` and `RESTORE_RUNBOOK.md` cover only Postgres. The `uploads` volume (`docker-compose.yml`) holds room photos, maintenance-task photos, and the property, spa and restaurant map images.
- **Scenario:** After a disk failure, the database restores, but every image path in it 404s: room pages lose their photos and the floor plans go blank.
- **Fix direction:** Add a tarball of the volume to the same job and retention, plus a restore step.

### M11. Open redirect after staff login
- **Where:** `sunset-beach/app/admin/login/page.tsx:27,63`.
- **Scenario:** `/admin/login?callbackUrl=https://evil.example/admin` sends a freshly logged-in staff member to a look-alike page, which can ask them to "log in again".
- **Fix direction:** Accept only same-origin relative paths that start with `/` and not `//`.

### M12. The POS ticket's poll can overwrite newer state
- **Where:** `sunset-beach/components/OrderTicket.tsx:181–188` and `lib/usePolling.ts`.
- **Scenario:**
  - A 3-second poll that started before a write can resolve after it, so `setOrder` puts the older order back on screen.
  - After a close returns `PAID`, a late poll response can briefly show `SENT` with the pay buttons enabled again; the server's unique constraint then rejects a second close.
  - A quantity tap computed from a stale quantity sends an absolute value (`PATCH` is a full replacement), which overwrites a change made from the other device.
- **Fix direction:** Track a request sequence number or the order's `updatedAt`, ignore older responses, and pause polling while a write is in flight.

### M13. Frontend "today" computed in UTC or frozen at module load
- **Where:**
  - `components/admin/PropertyMapView.tsx:65` and `SpaTableMapPanel.tsx:14`: `toDateKey(new Date())` gives the UTC date, so before 07:00 the property map highlights yesterday's arrivals and departures. `lib/hotelDate.ts` exists precisely to prevent this.
  - `ShiftCodeManager.tsx:15`, `PayRateManager.tsx:8`, `RosterGridImportManager.tsx:24`: `TODAY = new Date().toISOString().slice(0,10)` is the UTC date, evaluated once at module load. It defaults `effectiveFrom` to yesterday before 07:00, and goes stale across midnight.
  - `AttendancePanel.tsx:21` uses the same module-level `NOW`.
- **Fix direction:** Use `hotelDateKey(new Date())` at render time everywhere. `app/admin/(dashboard)/schedule/page.tsx:33` duplicates `hotelDateKey` inline.

### M14. The public booking site shows a total computed on the client
- **Where:** `sunset-beach/lib/publicQuote.ts`, `lib/quote.ts#mergeQuote`, `app/(site)/booking/page.tsx:75`, `app/(site)/booking/[roomId]/page.tsx`.
- **Scenario:** The guest sees a float sum of per-night prices, and any night missing from the pricing response silently adds `0`. The booking is then created at the server's own price, which can differ. This contradicts the frontend CLAUDE.md rule "Never display an amount computed on the client". The public site is outside the usual scope, so this is flagged rather than proposed for an immediate change.
- **Fix direction:** Add a backend quote endpoint for the public flow (there is already `POST /bookings/staff/quote`) and display its result.

### L1. Documentation drift in `CLAUDE.md` and the docs
- **Backend CLAUDE.md:**

  - The "Spa billing" section says the old `treatmentMenuItemId` column "stays … until … V53 to drop". V53 has already dropped it.
- **Frontend CLAUDE.md:**
  - "there are no DOM tests" contradicts `components/OrderTicket.test.tsx`, which renders the component (`renderToStaticMarkup`). The same file mentions that test elsewhere.
  - The COOKIE_SECURE/HTTPS note contradicts DEPLOY.md (see H11).
- `RosterExportService#chipCellStyle` still uses the old per-`kind` styling. CLAUDE.md already says so, so it's a known, documented divergence; listed here only for completeness.
- **Undocumented rules the code clearly follows, which should be written down:**
  - Every BFF route (`/api/session`, `/api/guest-session`, `/api/*-proxy`) calls the backend server-to-server, so the backend never sees the client's IP (see H2).
  - Order history is filtered by Payment time for `PAID` and by `updatedAt` for `CANCELLED`.
  - Room-service ownership is decided by `booking.guestEmail` matching the account email, while `/guest/bookings` lists bookings by `guestId` card. The two can disagree.

### L2. `Order.openedByUserId` is `string` in the frontend but nullable in the spec
- **Where:** `sunset-beach/lib/posTypes.ts:276,321,351`.
- **Scenario:** Room-service orders have no opener. `OrderHistoryTable` builds its staff dropdown from these values and ends up with a `null` key.
- **Fix direction:** Type it as `string | null`.

### L3. `OrderService.update` edits closed orders
- **Where:** `OrderService.update` (338).
- **Scenario:** It changes `tableId`/`note` on `PAID`/`CANCELLED` orders without a status check. The change is cosmetic but rewrites history.

### L4. QR tokens end up in access logs
- **Scenario:** QR ordering puts the guest access token in the query string (`/order/{id}?token=`), so it lands in nginx access logs. The token stays valid while the order is OPEN or SENT. This is acceptable for a QR flow; worth knowing when sharing logs.

### L5. One ledger account for card, transfer and cash
- **Scenario:** Card and transfer payments, folio payments included, debit account 1000 "Cash/Bank". `LedgerService.postFolioPayment` ignores `payment.getMethod()`. This matches CLAUDE.md's "Dr Cash", but cash reconciliation from the ledger can't separate the drawer from the card terminal.

### L6. Restore runbook publishes the database port
- **Where:** `RESTORE_RUNBOOK.md` §3.3.
- **Scenario:** It uses `-p 5434:5432` on all interfaces (see C2).

### L7. Minor operational bits
- Saving a maintenance task writes its photos to disk inside the DB transaction, so a rollback leaves orphaned files.
- Printer and attendance-device hosts are free-form (MANAGER/ADMIN). That is effectively an internal-network port scanner for those roles; acceptable given who holds them.

## Things checked and found sound
- Every spec operation is implemented, and every implemented route is in the spec. `EndpointCoverageTests` covers the `SecurityConfig` rules.
- The frontend's 174 hand-mirrored types match the spec's field names. Apart from M7 and L2, the frontend's nullability agrees with the spec.
- Money stays in `BigDecimal` throughout. Server-computed totals are respected, apart from the public quote (M14). The ledger rejects unbalanced entries.
- Uploads are protected against path traversal (`RoomImageService`, maintenance photos). Upload types are detected from content with Tika.
- JWT revocation works through `tokenVersion`, re-checked on every request. Staff and guest tokens use separate keys. The SiteMinder key is compared in constant time and path-scoped.
- The public proxy has a strict allowlist. CSP, `X-Frame-Options`, `nosniff` and SameSite=Lax httpOnly cookies are in place.
- No secrets in git history for either repo, apart from the deliberately fake test JWT secrets.
