# CLAUDE.md — sunset (backend)

Backend for a small resort's PMS + restaurant POS. Java 21, Spring Boot, PostgreSQL, Flyway, contract-first via `openapi.yaml`. Single hotel, single instance, on a server physically in the hotel.

Rules below were learned from real bugs. Where one looks arbitrary, the reason is stated — read it before deciding to do otherwise.

---

## Code generation

`openapi.yaml` is the source of truth and is edited by hand. Regenerate only with `scripts/generate-api.sh` — it carries the exact flags the committed code was produced with and is idempotent (running it twice changes nothing).

**Some generated files are hand-maintained and will be silently clobbered by a blind copy.** `scripts/generate-api.sh` is the definitive list of what it skips or patches — check it before trusting this summary:
- `AuthApi` is never generated at all, so there's nothing to clobber: `login()` needs an `HttpServletRequest` the generated signature can't carry, and `register()` would collide with `registerUser()` as two handlers on one route.
- `AuthResponse`, `LoginRequest` are fully hand-written, not templated output — deliberately no `toString()` override, so a stray log line can never print a raw JWT or password.
- `DeleteRoomImageRequest` is deliberately missing `@NotNull` on `path` so a null `path` produces the documented plain `ErrorMessage` (via `RoomController`'s manual check) instead of the `ValidationError` shape `@Valid` would trigger.
- `BookingCreateInput`, `UserCreateInput` stay in the generated copy, but a `sed` step in the script reapplies `@Email(message = "Invalid email")` after every regeneration — openapi.yaml alone can't express a custom Bean Validation message.

PII redaction in `toString()` is not manual any more: mark a property `x-sensitive: true` in `openapi.yaml` and the template renders `[REDACTED]`. `ToStringRedactsGuestPiiTests` fails if this regresses.

**A `nullable: true` + `required` property in openapi.yaml generates a `@NotNull` that rejects the very null it's supposed to allow.** The codegen's `JsonNullable<T>` wrapper unwraps before Bean Validation sees it, so `@NotNull` validates the unwrapped value, not the wrapper. Fix by omitting the field from `required:` and validating manually in the service — don't add it back to `required:` to "match the schema."

## Migrations

**A database that already exists is adopted, an empty one is built.** `V1` is an intentional no-op: the original tables were created by Prisma before this backend existed, and Flyway adopts that schema via `baseline-on-migrate`. `V1_1__prisma_baseline_schema.sql` recreates that Prisma-era schema for a genuinely empty database, so V2 onward apply unmodified: an empty Postgres goes through every migration to the current version and passes `ddl-auto=validate` (verified from scratch at V134 - 135 migrations, no errors). Don't edit V1/V1_1 to "tidy" this. Tests still bootstrap from a committed baseline dump (`test-db-baseline.sql`), purely as a speed optimisation.

**`ALTER TYPE ... ADD VALUE` and any DML using the new value must be in separate migration files.** PostgreSQL forbids using a freshly added enum value in the same transaction, and Flyway wraps each migration in one. See V2/V3 (new `Role` values) and V6/V7 (new `PrintDocumentType` value, then a backfill — V6's own comment explains the split).

**A set of values on one row is `TEXT[]` plus a `CHECK` constraint, not a native Postgres enum array.** `Role` is a native enum (one value per row); `JobFunction` (`User.jobFunctions`, a set) is not, deliberately — this project has a working Hibernate mapping for a scalar native enum and for a plain array (`RoomEntity.images` is the only array column here, and it's `text[]`), but none for an *array of a custom enum type*, and `V33__user_job_functions.sql` wasn't the place to become the first. The `CHECK` constraint is the DB-side validation a native enum would otherwise provide. Don't "fix" this inconsistency by converting it to a native enum array — read `V33`'s own comment first. It's a deliberate trade-off, not an oversight: it costs `JobFunction` the type safety a native enum gets, but it buys a real simplification — adding a third value later is one migration updating the `CHECK` constraint, not the `ALTER TYPE`-plus-separate-migration dance the rule above describes.

Some migrations are destructive (dropped columns, deleted rows) — V4 and V11 are the two so far. Code rollback alone is not safe once one of these has run; restoring means restoring a dump. Take one before deploying. Per-migration rollback notes (V132's "dump only once a fee exists") are in DEPLOY.md.

## Money

**The server computes every amount. A client-supplied price or total is never trusted, ever.** This holds for room rates, order totals, payments, and folio balances.

The one deliberate exception is a booking imported from SiteMinder (see its own section below): its price is SiteMinder's total, because the guest already agreed it on the OTA. It is still frozen per night like any other agreed price, and only `BookingWriter#insertExternal`/`#applyAgreedTotal` accept it. Don't widen this to any staff or public request.

**A guest sees a price only from the server.** `GET /public/rooms/{id}/quote` is the guest-facing counterpart of `POST /bookings/staff/quote` (same `BookingWriter#quoteStaff` computation, no room unit, own `PublicQuoteRateLimiter` bucket so quoting never uses up the eight-an-hour booking attempts). A guest client must show that figure, never a sum of `GET /public/rooms/{id}/pricing` days - the public web flow still does the latter (audit finding M14), the mobile guest app does not.

**Agreed prices are frozen per night** (`BookingSegmentNightlyRate`). Extending a stay prices only the new nights; already-agreed nights keep their original rate. Repricing an existing night happens only through the explicit reprice action, and only for nights from today forward. This exists because the system used to recompute the whole stay from current rates, so extending a booking by one night silently repriced the entire stay.

Undoing a relocation restores the preserved original rates. It is not a new agreement.

**A POS order is created with its first line, and an order with no lines can't be closed.** The POS screens send the first item in `POST /orders` (`OrderCreateInput.items`) instead of creating the order when a table is tapped - an opened-and-abandoned table used to hold the table busy and end up as a ฿0 `PAID` order. `OrderService#close` refuses an empty order (409). The rule is enforced at creation too: `POST /orders` with a `tableId` and no items is a 400 (spa-zone tables, the spa door's `spaAppointmentId` and room service's booking-only orders are exempt - they create first and add after), and closing a shift cancels, on the audit record, any abandoned empty `OPEN` order instead of blocking on it. The guest receipt and pre-bill show the VAT already inside the total ("incl. VAT 7%", `RevenueClassification.vatInside`) - a breakdown, never an addition; there is no service charge in this system. `CloseOrderInput.amountTendered` (CASH only) is checked against the total and written to the audit entry with the change; it is never what's charged.

**A sent line is voided, never edited.** `PATCH`/`DELETE` on a line stay `OPEN`-only; once the kitchen/bar has it on paper, `POST /orders/{id}/items/{itemId}/void` (MANAGER+, required reason) takes the quantity out of `OrderItem` and records it as an `OrderItemVoid` (V128), and a VOID ticket goes to the same station. Keeping voids out of `OrderItem` is the point: every reader that sums lines (the total, the ledger posting at close, Z410, the spa missing-treatment check, receipts) stays correct without knowing voids exist - don't fold them back in as a flagged `OrderItem` row. `voidItem` and `close` both lock the order row `FOR UPDATE`, so a void can't change the total between close reading it and charging it. **Cancelling a whole `SENT` order is the same kind of void:** `POST /orders/{id}/cancel` on an order with sent lines is MANAGER+ (403 otherwise) and needs a `reason` (400), and it voids every sent line through the same `OrderService#recordVoid`/VOID-ticket path (lines leave `OrderItem`, so the total is 0), drops lines that were never sent, and audits `ORDER_CANCELLED` with the reason. The role check is in `OrderService#cancel`, not `SecurityConfig`: the route floor is WAITER and can't see the order's status. An `OPEN` order (nothing sent) is still a waiter's call and keeps its lines. Do not "simplify" this back into a flag on `OrderItem`.

`Order.number` (V128) is the receipt number - one global DB sequence, printed on every ticket/receipt and shown next to the id, never instead of it.

## Ledger

**Double-entry, immutable, no backfill.** `LedgerService` is the only writer of `JournalEntry`/`JournalLine` (V120) and refuses any entry whose debits and credits differ. Posted entries are never edited or deleted; a mistake is corrected by a reversing entry (`reversesEntryId`, unique, so at most once). Only activity from V120 forward is in the ledger - Z120 (trial balance) won't reconcile with Z410/occupancy for earlier periods, and that is expected. **Known gap from V132 on: Z410 (revenue statistic) and the manager report leave out `Booking.earlyDepartureFee`, while Z120 includes it** - both reports build room revenue per night from `ReportService#segmentsInRange`, the fee has no night, and the `PAID` settlement posts it to Room Revenue along with the stay. For any period with early checkouts charged in full, Z410/the manager report will be lower than Z120's Room Revenue by exactly those fees. Not a bug to chase in the reports: closing it means a deliberate decision on where the fee shows (e.g. its own line dated by checkout), not folding it into a night.

**Automatic postings run inside the business operation's own transaction - the one exception to "accompanying writes never break the operation" below.** A close or settlement the ledger silently missed leaves a trial balance that still balances but no longer matches reality, which is worse than the operation failing. The hooks: `BookingService#updateStatus` (into `PAID` posts the room settlement at `totalPrice + earlyDepartureFee` - Dr Guest Ledger for the part already paid through folio payments, Dr Cash for the rest - out of `PAID` mirrors every unreversed settlement; the booking row is locked `FOR UPDATE` so two concurrent "mark PAID" requests can't both post - `LedgerBookingSettlementRaceTests`), `OrderService#close` (Dr Cash, or Guest Ledger for `ROOM_CHARGE`), `BookingService#recordFolioPayment` (Dr Cash, Cr Guest Ledger). A price change on an already-`PAID` booking still posts nothing. POS revenue splits FNB/SPA via `RevenueClassification`, shared with Z410 so the two can't drift.

**One balance per booking, and `PAID` follows it.** `BookingService#computeFolioBreakdown` is the only place "what does this guest owe" is computed: room (`totalPrice` + `earlyDepartureFee`, nothing once `CANCELLED`) + POS room charges, minus folio payments (applied to POS charges first, then the room), minus `settledOutside` - the room part not covered by folio payments on a booking marked `PAID` by hand (OTA prepayment, bank transfer). `balanceDue` is what check-out, the Today board, the property map and the booking page all show. The folio form takes any amount up to it, room included, and `recordFolioPayment` sets `PAID` itself once the room is covered. Before this, "Total due" ignored both payments and `PAID`, the form could only take POS charges, and the desk couldn't tell what to collect. A folio payment carries the recorder's open cash shift (`FolioPayment.shiftId`, V132), and its cash counts in that shift's expected cash.

**An early checkout can shorten the stay; staff choose each time whether the released nights are charged.** `BookingOccupancyService#checkOut` with `shortenStay` moves `checkOut` to today (never before the first night) through `BookingService#updateSchedule` - not a parallel path - so availability, the calendar, the night audit and the reports follow on their own. `chargeUnusedNights` keeps the released nights' agreed price as `Booking.earlyDepartureFee` (V132): `totalPrice` stays "nights actually stayed" for every per-night reader, and the fee is owed on top. **On a relocated booking the early checkout can also drop whole trailing rooms:** `BookingWriter#updateSchedule(..., earlyDeparture = true)` (set only by `checkOut`, never by `PATCH .../schedule`, which still refuses to cross a relocation boundary) deletes every segment that starts on or after the new `checkOut` - a guest leaving before the move into the second room never uses it - and shortens the segment holding the new last night; the room passed in is that segment's, not the last one's. Leaving the segment alone and telling staff to "undo the relocation" first is what the old code did. Guest LTV counts it as room revenue; the per-night revenue reports (Z410, manager report) don't - there's no night it belongs to. **Check-out marks dirty the room the guest is in at that moment** (`BookingOccupancyService#currentRoomUnitId`, read before an early departure drops trailing segments - a move that took effect today puts them in the new room, which the shortened stay forgets); it never re-marks rooms they left earlier (that dirtied rooms housekeeping had cleaned). **The room a guest moved out of is marked dirty when the move takes effect:** at once for a move effective today or earlier (`BookingService#relocate` -> `markVacatedRoomDirty`, `CHECKED_IN` guests only, not if already dirty), and for a move planned for a later day by `VacatedRoomHousekeepingService` - a `@Scheduled` job (hourly at :05 Bangkok, so 00:05 is the real run and the rest are the catch-up after downtime) that claims the hotel day in `HousekeepingSweep` (V145) and so runs once per day: a repeat run never re-dirties a room cleaned meanwhile; a room another booking holds tonight is skipped. A checkout with a balance owed audits `checkout confirmed with ฿X unpaid` against the acting user.

## SiteMinder import

One-way, SiteMinder → us: our own polling script (not in this repo) scrapes SiteMinder's reservation screens and posts each reservation to `POST /integrations/siteminder/reservations`. `SiteMinderImportService` decides whether that's a create, an update, a cancel, or nothing. Nothing is ever pushed back.

- **Idempotency key:** `Booking.source = SITEMINDER` plus `Booking.externalReference` (SiteMinder's own reference), unique together (V123). There's no separate `externalSource` column, because `source` already says how a booking got in.
- **It reuses the staff paths and doesn't write around them.** A date change goes through `BookingService#updateSchedule`; a party-size change and a cancellation go through `BookingService#updateStatus`. So a SiteMinder cancellation releases the room, reverses a `PAID` booking's ledger settlement, and is counted by the manager report, exactly like a staff one. Creation is `BookingWriter#insertExternal`, which runs the same availability check. No availability means 409; an overbooking is resolved by a person.
- **Auth:** the first system-to-system caller this API has. `IntegrationKeyAuthFilter` checks `X-Integration-Key` against `SITEMINDER_INTEGRATION_KEY` (unset means off). It only acts on the import path and grants `INTEGRATION_SITEMINDER`, never a `ROLE_`. That path-scoping is what stops the key from satisfying the `authenticated()` rules on other routes, so keep it.
- **Audit:** `AuditLogService.record` writes an `IntegrationPrincipal` as actor `SITEMINDER` with a null role. The reused staff paths therefore audit themselves, and there are no SiteMinder-specific booking actions.
- **Guests are never matched by name.** Every new reservation gets a new name-only `Guest` card (`GuestLinkService#createNameOnlyCardForBooking`). A wrong name match would show the stay in a stranger's guest account. Contacts will come later through a separate enrichment pass keyed on `externalReference`.
- **Room type names** go through `SiteMinderRoomTypeMapping` (MANAGER+ CRUD, case- and space-insensitive). An unmapped name is a 400 on `roomTypeName`, never a guess. A room-type change on an existing reservation is a 409, because no path changes a whole stay's type.
- **An already-cancelled booking is never written to again** by a re-poll. The manager report dates cancellations by `updatedAt`, so even a timestamp touch would move the cancellation to another day.

## Spa billing

**What links a POS order to a spa appointment is presence, not a status.** `SpaAppointment.orderId` is set once — explicitly by the spa billing door (`POST /orders` with `spaAppointmentId`) or by `OrderService`'s own auto-link (by table, then by booking, tried at different moments — see `OrderService#autoLinkSpaAppointment`'s own javadoc) — and answers exactly one question: is this the order that bills this appointment's treatment. `Order.bookingId` is not the same fact and never was — see that field's own openapi.yaml description; the record of what a *closed* order was actually charged to is `Payment.bookingId`, set independently at `POST /orders/{id}/close`.

**Multi-treatment: a child row per treatment, no frozen price.** `SpaAppointmentTreatment` (`V50__spa_appointment_treatment.sql`) is one row per treatment on an appointment — the same treatment booked twice is two rows, not a quantity of two. `SpaAppointment.durationMinutes` stays a maintained sum over those rows (recomputed on every add/remove, never derived on the fly), specifically so both `EXCLUDE USING gist` constraints keep reading one plain column and never need to know the treatment table exists. `SpaAppointmentTreatment` freezes `durationMinutes` at add time (same "agreed terms are frozen" precedent as `BookingSegmentNightlyRate`) but deliberately **not price**: a room night bypasses the POS `OrderItem`/menu system entirely (`Payment.method=ROOM_CHARGE` reads `Booking.totalPrice` directly), so freezing there protects the only price authority that charge has. A spa treatment bills through the ordinary `OrderService#addItems`, which has exactly one pricing rule project-wide — read the menu live at the moment a line is added to an order. Freezing a second price on the appointment would manufacture a number that can silently disagree with the one actually charged, not protect a guest-facing quote (no price is shown when an appointment is booked). `SpaAppointmentTreatment.currentPrice` on the DTO is a live, unstored `MenuItem.price` read at response time — same "denormalized, not frozen" convention as `treatmentName` — shown for reception's own reference and never read by any billing path. Adding a treatment is legal only while `status` is `BOOKED` (growing `durationMinutes` can collide, same `translateOverlap` 409 handling as `create`); removing one is legal through `BOOKED` or `COMPLETED` (shrinking can never create a new overlap, so it never risks a 409) but always leaves at least one row — an appointment cannot exist with zero treatments. The old singular `SpaAppointment.treatmentMenuItemId` column stays on the table, unused by any code, until a full reader sweep clears it for `V53` to drop.

The billing *warning* is a separate question from the link, asked by the server, not by `OrderService`: `SpaAppointment.missingTreatmentNames` names which of this appointment's treatments the linked order doesn't (yet) carry, computed only once `status` is `COMPLETED` (empty for every other status, regardless of `orderId`) as a multiset comparison — for each `treatmentMenuItemId`, does the linked order's item quantity for it meet or exceed how many times this appointment booked it. **A `CANCELLED` linked order counts as carrying nothing of the appointment's treatments**, same as no order at all — a cancelled order keeps its items and keeps the link (nothing clears `orderId` on cancel), but it bills nothing, so treating its items as still-billing would let the warning go quiet on an appointment nobody actually charged. Presence still decides the *link*, completeness decides the *warning* — don't fold the two questions back into one gate. `SpaAppointmentService#getSchedule` (the day-grid read) computes this batched, not per-appointment: it only fetches order/order-item rows for appointments that are actually `COMPLETED` with a non-null `orderId`, via `OrderItemRepository#findByOrderIdIn`, so a day of mostly-`BOOKED` appointments costs nothing extra regardless of how many there are. The single-appointment write paths (`create`, `addTreatment`, `removeTreatment`, `updateStatus`, `updateSchedule`) share the same completeness computation (`SpaAppointmentService#computeMissingTreatmentNames`) fed per-appointment inputs instead — one method, two call shapes, so the batched and single-appointment reads can never silently diverge on what "missing" means.

**The spa checks who it books, on the server, on create and on reschedule.** The therapist must be an active `THERAPIST` (400), the table must be in the `SPA` zone (400), and the booking must be one the spa can serve on that date: in the house (`CHECKED_IN`) or not yet arrived (`NEW`/`CONFIRMED`/`PAID`, `EXPECTED`), and in both cases `checkIn <= date <= checkOut` (400 - a guest in the house is held to it too; the old "only warns" is gone, and with it `SpaAppointmentResult.warning`); cancelled, checked-out and no-show bookings are 409. **A treatment never starts in the past** (400, `requireNotInThePast`, hotel `Clock`): an earlier day is refused, and today the earliest start is the slot that is under way (10:20 -> the 10:00 slot of the 30-minute grid from opening time). `PAID` is allowed on purpose: it is a commercial status (a prepaid guest is the one most likely to book a massage), not "already left". These live in `SpaAppointmentService#requireTherapist/requireSpaTable/requireServable`, shared by `create` and `updateSchedule`; `swapTables` moves only the table between two existing appointments and needs none of them.

**Cancelling a booking cleans up its spa, in the same transaction (`SpaBookingCancellationService`).** Every `BOOKED` appointment is cancelled (reason "Booking cancelled"), and the still-unpaid `SPA`-department lines on the order linked to it are taken off (`OrderService#removeUnpaidSpaLines`: other departments' lines stay; an order left with no lines is cancelled; no `OrderItemVoid`, because a treatment never goes to a printer so there is no paper to void). **Anything already paid is left exactly as it is** - the appointment stays `BOOKED`, its `PAID` order untouched - and surfaces as `Booking.warning` (on the `PATCH` response and on `GET /bookings/{id}` for a cancelled booking, read fresh each time, never stored, so it clears once staff refund and cancel the appointment). `COMPLETED` appointments are delivered treatments and are never touched. The unconfirmed-booking expiry sweep calls the same cascade. **A stay that gets shorter does the same for what falls outside it** (`SpaBookingCancellationService#onStayChanged`, called from `BookingService#updateSchedule` next to the gym's `onStayChanged`, so a schedule edit, an early check-out and a SiteMinder date change all go through it): `BOOKED` appointments that have not ended and lie outside `checkIn..checkOut` (both ends inclusive) are cancelled with the same clean-up; a paid one is left as it is. The SiteMinder and sweep callers have no staff principal, so `cancelledByUserId` stays null and the audit rows go through `recordSystemAction` (or `record` for SiteMinder).

**A partly-paid spa bill is topped up, not re-created.** `POST /spa-appointments/{id}/bill-missing-treatments` adds exactly the missing quantity of each treatment (the same multiset comparison as `missingTreatmentNames`) to the appointment's own order through `OrderService#addItems` - live menu prices, nothing charged. It needs a `COMPLETED` appointment that already has an order. **An appointment can have several orders:** `SpaAppointment.orderId` stays its own, first order and the further ones are rows of `SpaAppointmentOrder` (V144, one row per order, an order belongs to at most one appointment). What an order "carries" and the `missingTreatmentNames` warning are counted over all of them (cancelled ones excluded) - in the day grid (`getSchedule`, batched) and in the single read alike. The top-up goes onto the first linked order that can still take lines (`OPEN`/`SENT`); if none can (all `PAID` or cancelled) a new order is opened on the appointment's table, linked **before** its lines are added (so the spa auto-link can't attach it to another appointment on the same table) and billed for just the missing quantity. Booking cancellation (`SpaBookingCancellationService`) treats the appointment as paid if any of its orders is `PAID`, and clears the unpaid spa lines off every order. `removeTreatment` is 409 once any linked order is `PAID`: a paid treatment is refunded through the order, not deleted from the record.

## Gym reservations

**The gym is exclusive and the database says who got the slot.** `GymReservation` (V142) has a range-only `EXCLUDE USING gist` (`gym_reservation_no_overlap`, `BOOKED`+`COMPLETED` hold the slot) - no check-then-write; a conflict is recognised by SQLSTATE `23P01` (`GymReservationService#translateOverlap`). The 120 minutes a day per hotel booking cannot be a constraint, so create/move/cancel lock the `Booking` row first (`findByIdForUpdate`, always booking before reservation) and sum under the lock - `GymReservationServiceTests` races both. Only a guest with a `CHECKED_IN` booking of their own account books (403 otherwise, someone else's reservation is 404); staff (CASHIER+) may also book an `EXPECTED` guest. A cancelled hotel booking and a check-out cancel every reservation that has not ended (same transaction, `GymReservationService#onBookingEnded`, like the spa's cascade).

**A change of the stay's dates takes the sessions outside it with it** (`BookingService#updateSchedule` -> `GymReservationService#onStayChanged`, the one path that changes dates: the schedule form, an early check-out, the SiteMinder import). A session in progress is cancelled like any other and the automation switches the equipment off. **Narrowing the hours never cancels**: `PUT /gym/settings/hall` without `force=true` saves nothing and returns the future reservations the new hours would leave outside (`saved: false`); with `force=true` it saves and still lists them. The schedule keeps showing such reservations.

**Race tests assert invariants, not a winner.** `SpaAppointmentOverlapRaceTests#concurrentSwapAndCreate...` used to expect "exactly one succeeds", but the create can never win there (tableB is held by B, then by A), and PostgreSQL's deadlock victim between the swap's forced check and the create's insert is whoever hits `deadlock_timeout` first - on a loaded machine sometimes the swap, so nobody succeeded and the test failed about one full run in several. Now: the create always loses, the swap wins or is told to retry, and the state left behind must match whichever happened. Assert the invariant the system guarantees, never the scheduling of two threads.

**The equipment automation sends only at transitions, remembers in the database and never polls.** See `GymAutomationService`'s javadoc and DEPLOY.md. The things that are not obvious: switch-ons are processed before switch-offs in a run (a session ending as the next one's switch-on falls due must find it registered, or the switch-off would cut the next warm-up); the "keep it on" test for a switch-off is "another unfinished session starts within `leadMinutes` of this one's end (of now, for a cancellation) or has already had its switch-on sent" - not just the former, or a late sweep switches off in the middle of the next session's warm-up; a covered second session (`COVERED_BY_PREVIOUS`) still counts as "was on" for its own switch-off; status changes made by the sweep are conditional `UPDATE`s, never a full-entity save, so a cancel racing the sweep is not overwritten. Commands go through `GymDeviceService#commandRelayForAutomation/commandAcForAutomation` - the same Tuya calls as the Gym page, without the confirming read and without the staff audit (the sweep writes one system entry per phase with `recordSystemAction`). Tests move a `MutableClock`; the production sweep interval is overridden to an hour in them so the background run cannot race an explicit `runOnce()`. **Whether the automation can work at all is answered without Tuya:** `GET /gym/status` (`tuyaConfigured` from the server's keys, `automatedDeviceCount` = active devices with `inBookings`) - the Gym pages show "Tuya is not configured" from it the moment they open, and a reservation panel with no key or no participating device says "Automation not set up" instead of "Equipment not switched on yet".

## Lighting (WLED)

**An admin types a host and the server sends HTTP requests to it - that is an SSRF surface, and `LanAddressGuard` is what closes it.** A controller's host is accepted only when *every* address it resolves to is private IPv4 (10/8, 172.16/12, 192.168/16) **and inside `app.lighting.allowed-cidrs`**; loopback, link-local (169.254.x.x - cloud metadata), "this host", multicast, IPv6, anything public and any address of one of this machine's own interfaces are refused. The own-interface rule alone is not enough: the other containers on the compose network (the database, the frontend) live in 172.16/12 too and are not *this* container's address - which is why **`LIGHTING_ALLOWED_CIDRS` is required, and unset or blank means lighting is off** (`LanAddressGuard#isConfigured`; a malformed value still fails startup). Off means: `GET /lighting/status` says `configured:false`, `GET /lighting/devices` is a 200 with `configured:false` and no devices, and the calls that make the server send a request (`POST .../state`, `POST /lighting/settings/devices`, `.../check`, a `PATCH` that *changes* host or port) are 409 "Lighting is not configured on the server"; listing, renaming, deactivating, reordering and deleting saved devices keep working (an unchanged host re-sent by a form is not a change). Don't default the variable to "all private ranges" to make a fresh install work - that default is the hole. **The check runs on every request, not only on save, and the request goes to the resolved IP, not to the name** (`HttpWledClient`): a DNS answer that changes after the check (rebinding) has nothing left to change. Redirects are never followed (a 3xx is a failure - this is also why the IP, not a name, is in the `Host` header: WLED's captive-portal 302 only fires for a name). The response body is capped (1 MB) and a hard deadline covers the whole exchange including a trickled body. **A device's response is parsed, never copied into an error** - messages are in our own words (`did not answer in time`, `answered with an error (HTTP 500)`); details go to the log. Don't add a "show the raw answer" to a failure message.

**There is no password field because WLED's JSON API has none.** The OTA lock and the settings PIN protect firmware update, `/edit`, `/upload` and `POST /json/cfg`; `POST /json/state` and `GET /presets.json` are open on the LAN by design (WLED's own docs: anyone with network access has permission for any operation). The network is the security: the controllers are reachable only through the wg-hotel tunnel, and only MANAGER+ can send a command (`SecurityConfig.LIGHTING_CONTROL_ROLE` - the one line to change); the controller list and the address test are ADMIN.

**Nothing polls, like the gym.** A controller is contacted when the page asks for the list (all active ones in parallel, each bounded by `app.lighting.request-timeout-ms`, so one dead controller costs one timeout and the rest still return `online:false` + `stateError` for just that one), and after a command (read back, so the answer is what WLED reports, not what was asked for). State and the preset list are cached for `app.lighting.state-cache-seconds` (10) to absorb several people opening the page; `refresh=true` bypasses it and a failed read is never cached. Don't add a background refresh: a controller on a flaky wireless link is expected to be offline sometimes, and a sweep would only turn that into log noise.

**Notes on WLED's behaviour that are easy to get wrong:** `bri` 0 means off, and with no `on` in the request WLED derives `on` from `bri`; `ps` is -1 when no preset is applied and WLED clears it when the look is changed by hand, so `presetId: null` does not mean "never a preset"; a preset is applied a moment after the request (`app.lighting.confirm-delay-ms`), so the read-back can lag. `/presets.json` is read tolerantly (object keyed by id, name in `n`, id 0 and non-objects skipped) because its structure is not documented. Command failures are audited like successes (`LIGHTING_DEVICE_COMMAND`), whoever sent them.

## Print layouts

**Every configurable printed document - guest receipt, pre-bill, kitchen ticket, bar ticket, Z-report - is laid out by one pure class, `PrintRenderer`, and the settings page's preview comes from the same call.** `PrintLayout` (V137, one row per document type, `/settings/print-layouts/**` ADMIN-only) holds paper width (58/80mm, of the printer that document goes to), body font (the printer's built-in Font A or B), title, 1x/2x sizes for title/items/location/total, header/footer text, which optional lines print and, for the two guest-facing documents, the logo. The printing code builds a content record (the document's words, money and ids already formatted) and hands it with `PrintLayoutService#style(doc)` to `PrintRenderer.receipt/ticket/voided/report`; `toEscPos` turns the result into bytes and `POST /settings/print-layouts/{doc}/preview` turns the same result into JSON lines. Don't add a second layout path "for the preview" - the point is that what wraps or gets cut on screen is what happens on paper. The seeded defaults reproduce every document byte for byte as it printed before layouts existed (`PrintRendererTests#*Defaults_produceByteForByte*` for receipt, kitchen ticket, void ticket and Z-report) - keep those green when touching the layout. One table holds every column for every document; which fields a document reads is in `PrintLayoutInput`'s openapi description, and the editor (`lib/printLayout.ts#PRINT_CONTROLS`) offers only those - keep the two in step.

- **A thermal printer has no arbitrary fonts.** "Fonts" means Font A/B (`ESC M`), 1x/2x (`GS !`) and bold. Column counts are the printer's usable ones, not the dot width: 80mm is 42 (A) / 56 (B), 58mm is 32 / 42. A 2x line holds half as many, so a doubled title, item, location or total is laid out for `columns / size`.
- **The Z-report's rows live in `ZReportContent`, shared by the real report (`ShiftService`) and the editor's sample**, so they can't drift. Its figures are never configurable - title, font, header, footer and the "Closed" line are.
- **A void ticket follows its station's layout (font, sizes, location/order/time) but always carries the fixed title "*** VOID ***"** and always prints the reason; it never shows the header/footer/logo.
- **Samples end with "- sample, not a real order -"** so a test print sent to the kitchen or bar printer is never mistaken for an order. Test print goes through the normal queue on the document's department's printer (kitchen ticket: KITCHEN, bar ticket: BAR, the rest: CASHIER) with the *saved* layout, not the editor's unsaved one.
- **The logo is one shared image (`PrintLogo`), stored as a gray-valued RGB PNG (max 576x400) and dithered at print time** (`ReceiptLogo`: Floyd-Steinberg to paper dots x `logoWidthPercent`, width a multiple of 8, raster `GS v 0`). It is deliberately an RGB image with r=g=b, not `TYPE_BYTE_GRAY`: Java converts through a linear gray colour space when such an image is drawn, which washed every mid-tone out (caught by `ReceiptLogoTests#midGray_isDitheredToAMixOfBlackAndWhite`). Only the receipt and pre-bill print it. JPEG and PNG only - the JVM has no WebP decoder, so WebP is a 400 even though `ImageUploadValidator` sniffs it. Removing the logo turns `showLogo` off on every layout. Uploading it audits `RECEIPT_LOGO_CHANGED`.
- **A print job replays its stored bytes**, so a layout change never alters documents already queued - only the next one built.
- Header/footer are stored with blank lines dropped and each line trimmed (up to 6 lines x 48 characters). Layout changes audit as `RECEIPT_SETTINGS_UPDATED` (the name predates the other documents) naming the document and the changed fields, never their values; an unchanged `PUT` writes nothing.
- **`"ReceiptSettings"` (V136) is left in place, unread, after V137 copied it into the receipt and pre-bill rows** - dropping it is destructive and buys nothing until V137 has run in production. A later migration removes it.

## Guest lifecycle emails

**Automated guest email (pre-arrival, post-stay, win-back) goes only to a verified, not-opted-out `GuestAccount` - never to a bare `Guest` card.** Everything else this system emails a guest is something they caused (verification, a booking status change). These aren't, so the one population with a consent basis is people who created an account and confirmed their email. A card staff typed in at the front desk is not that. Widening the audience is a separate, deliberate decision about consent, not a query tweak. The address used is the account's verified one, not the booking's snapshot `guestEmail`. One opt-out (`GuestAccount.marketingEmailsOptOut`, via the stable `unsubscribeToken` link) stops all three.

`GuestEmailLog` is both the sweep's idempotency record and the guest card's email history, so a row is written only after `EmailService` reports the email actually went out (the lifecycle methods return a boolean; an unset `RESEND_API_KEY` returns `false`). The sweep is deliberately not `@Transactional` - one transaction would roll back rows for emails that had already been sent. `GuestEmailLog.sentAt` is set from the shared `Clock` (hotel wall-clock), not `@UtcCreationTimestamp`, because the win-back window compares it against a `Clock`-derived cutoff; it's zoned with the clock's zone on output, never `TimestampFormat.toUtc`.

`LifecycleEmailSettings` is a singleton row (`id = 1`, pinned by a `CHECK`, seeded by V112, every type disabled until an admin turns it on). `/settings/**` is ADMIN-only, reads included.

## Payments, states and exports (owner's decisions after the October 2026 QA report)

**A debt is visible whatever the status.** `BookingFolioCalculator` is the one place the folio balance is computed (`BookingService#computeFolioBreakdown` and every list delegate to it), and `Booking.balanceDue` rides on every booking the API returns - lists and searches compute it for the whole page in two queries, not per row. A client's "Owes" badge reads `Booking.owes` and `balanceDue` and nothing else: `owes` (`BookingFolioCalculator#debtHasFallenDue`) is true only when `balanceDue > 0` **and** the debt has fallen due - a guest in the house or gone (`CHECKED_IN`, overdue departure included, `CHECKED_OUT`), a `CANCELLED` booking (what is left is charges), or a stay whose dates are over; a future unpaid booking owes nothing yet. **A no-show's room is not owed, and neither is a past stay nobody arrived for** (dates over, still `EXPECTED`, not cancelled: `BookingFolioCalculator#neverArrivedAndOver`); the night audit lists those in its own `notArrived` block ("mark no-show or cancel") instead of `missedArrivals`/`unpaidBalances`. **A no-show's room is not owed** (`FolioBreakdown#roomOwed` is zero for `NO_SHOW`, like `CANCELLED`): it reaches "Unpaid balances" only through other charges; unmarking the no-show brings the room back, since it is derived. `GET /night-audit` has an `unpaidBalances` block: finished stays (checked out, past `checkOut` and not in the house, or cancelled) with `balanceDue > 0`, any status.

**`PAID` never writes money off.** A change into `PAID` while `BookingFolio.amountToMarkPaid` (the folio as if the booking were not yet paid or cancelled; also in `BookingService#settleForPaid`) is above zero is a 409 unless `BookingStatusInput.payment` carries exactly that amount; the payment is recorded in the same transaction (`insertFolioPayment`, shared with `recordFolioPayment`, so cash shift, ledger posting and audit can't drift). The old hand-set `PAID` ("collected outside": OTA, bank transfer) is now a payment with method `OTHER`. `settledOutside` stays in the folio maths only for `PAID` rows that predate this rule, and a `PAID` booking's settlement can still post "Dr Cash for the rest" for them. The dashboard's room figure is `PaymentsSummary.folioPaymentsTotal` (recorded `FolioPayment` rows) - never a sum over bookings by status; don't derive revenue from a status anywhere (`RevenueExportService`'s "Paid bookings (info)" sheet is explicitly not a total).

**States are enforced by the server, not the UI.** Check-in: not `CANCELLED`, not before `checkIn` (hotel `Clock`), not repeated (409). Check-out: only `CHECKED_IN` (409). `ROOM_CHARGE` close: only a `CHECKED_IN` booking (409; an overdue guest is still `CHECKED_IN`). Changing dates, relocating or repricing a `CHECKED_OUT` stay is 409 (`requireStayNotEnded`) - it would add charges to a closed folio. A `PAID` booking is checked in like any other: the rule is "not cancelled", not "only NEW/CONFIRMED".

**A guest who has arrived is not cancelled.** `BookingService#updateStatus` answers a change into `CANCELLED` with 409 when `occupancyStatus` is `CHECKED_IN` or `CHECKED_OUT` (the folio, the room revenue and the room itself belong to a stay that is happening or happened - check out / shorten the stay instead). Only a real change is refused: re-sending `CANCELLED` to an already-cancelled booking is still a no-op, and a SiteMinder cancellation of such a booking comes back `SKIPPED` with a message rather than failing the poll every cycle. The admin screens don't offer the option (`lib/bookingStatusChange.ts#selectableStatuses`), but the rule is the server's.

**A cash shift is blocked only by its own orders.** `ShiftService#close`: an `OPEN`/`SENT` order opened by the shift's cashier (or carrying a payment in that shift) blocks with a 409; anyone else's open order is listed in `Shift.warning` on the close response and left alone. Empty `OPEN` orders are still cancelled on the audit record, system-wide. **A drawer that doesn't match needs a note:** counted cash different from the expected (float + cash payments + folio cash) is a 400 on `notes` without one (blank or only invisible characters counts as none); a matching drawer needs none.

**Exports go through `SpreadsheetSafe`.** A cell starting `=` `+` `-` `@` tab or CR gets a leading `'` (CSV: `CsvBuilder`; workbooks: `SpreadsheetSafe.sanitize(workbook)` before `write`). A cell that is only a number (`-50.00`) is left alone - its sign is data. `RosterGridImportParser` undoes the apostrophe on re-import (`unescape`). A new export calls the utility; it never builds a cell by hand.

**Names are trimmed in the model, not the service.** A property marked `x-trim: true` in `openapi.yaml` is stripped (`com.sunsetbeach.util.NameText.strip`: every Unicode space separator, no-break space and zero-width character, not just what `String#strip` treats as whitespace) by the generated setter, fluent setter *and* required-args constructor (`openapi-templates/pojo.mustache`; Jackson uses the constructor when it can, so trimming only the setter silently did nothing), and its `minLength` then rejects a name of only spaces with a 400. Mark every new required name/label that way. Optional nullable names (`JsonNullable`) are trimmed in the service.

**A POS line is 1..99** (`OrderItemInput.quantity`, and the merged total in `OrderService#addItems`). **A guest-facing order path (dine-in QR, room service) accepts only what `GET /public/menu` lists** (`MenuService#isPubliclyOrderable`, checked for the whole request before anything is written).

## Concurrency

Availability writes run `SERIALIZABLE` in `BookingWriter`, and PostgreSQL serialization failures (SQLSTATE 40001) are translated to `ConflictException` with a human message. `BookingWriter` is a separate bean specifically so the `@Transactional` proxy applies — self-invocation would bypass it.

**Recognise a database failure by its SQLSTATE, never by message text.** Message wording isn't part of Postgres's own contract — it can vary by server/driver version and locale, and some failures don't name what they were checking when they landed at all. `SpaAppointmentService#translateOverlap` used to match the violated exclusion constraint's own name inside the exception's message; that works for a genuine overlap (the message does name the constraint) but is structurally blind to a deadlock (SQLSTATE `40P01`), whose own message names the *relation* it was checking a constraint on, never the constraint itself. A real, reachable deadlock between this service's own deferred-then-forced-immediate check (`swapTables`) and a concurrent ordinary write checking the same range escaped as a raw, untranslated 500 instead of the same "try again" conflict every other race in this system gives — found only because it fired once under load running the whole suite together, not from reading the code. Walk the cause chain for the actual `java.sql.SQLException` and compare `getSQLState()` instead (see `com.sunsetbeach.error.SqlStates`, shared by `BookingService#isSerializationFailure` for `40001` and `SpaAppointmentService#translateOverlap` for `23P01`/`40P01`) — never re-derive what kind of failure this is from prose that was never meant to be parsed.

Do not copy `SERIALIZABLE` to writes that do not contend for inventory. POS order and payment writes use ordinary transactions; using SERIALIZABLE there would produce spurious conflicts during service hours.

Where a race is better solved by the database, use the database. Four tools exist here for four different shapes of conflict, and picking the wrong one either misses real races or produces spurious ones:
- **SERIALIZABLE** (`BookingWriter`) — when availability itself has to be recomputed from several sources (unit counts, blocks, other segments) and can't be expressed as a single row-level constraint.
- **A unique constraint** — when the rule is "at most one," not "no two may overlap": one payment per order is enforced this way, not by a check-then-write.
- **A Postgres `EXCLUDE USING gist` constraint** — when the rule is "no two rows may overlap on a range," and the database can express that directly. The spa module uses one per axis (`spa_appointment_no_table_overlap`, `spa_appointment_no_therapist_overlap` — see `V41__spa_appointment.sql`/`V43__spa_appointment_completed_still_occupies_slot.sql`) instead of a pre-write query: `SpaAppointmentService` never checks for a conflict before writing, it writes directly and lets the constraint reject, translated to a human message by `translateOverlap` — by SQLSTATE first (see this section's own rule on recognising database failures), the constraint's own name only decides which of the two sentences to return. This is cheaper than SERIALIZABLE and correct here specifically because the check needs no unit-counting or block-checking — just "does this interval overlap that one" - which is exactly what the constraint already computes.

- **A transaction-scoped advisory lock** (`GuestRepository#lockEmail`) — only for find-or-create where the natural unique constraint *can't* exist because the data already violates it. `Guest.email` has duplicates in production, so no unique index; `GuestLinkService` locks the normalized email before "look up, create if none" so two concurrent callers can't both create a card — which would make that email ambiguous, and so unlinkable, forever after. Prefer a unique constraint wherever the data allows one.

**Swapping two rows across an exclusion constraint needs the constraint deferred, not a clever statement.** `SpaAppointmentService#swapTables` (table-only: date/startTime/therapistUserId/durationMinutes never move on either side, which is what makes it well-defined regardless of how long either treatment runs) looks like it should be two ordinary `UPDATE`s — and three people in a row reasoned their way to an implementation that doesn't work before this one shipped. Read this before trying another:
- **A single statement moving both rows, against a `NOT DEFERRABLE` constraint, does not work.** The theory was that Postgres checks a constraint like this once, at the end of the statement — true for a `DEFERRABLE` constraint left `INITIALLY IMMEDIATE`, false for one that is not deferrable at all. `NOT DEFERRABLE` is enforced synchronously, per row, as each row's GiST index entry is written — so a single `UPDATE ... CASE id WHEN ...` moving both appointments still finds the other one sitting on its target table, regardless of row-processing order, whenever the two appointments' times actually overlap (the only case a swap is worth doing at all). Proven wrong in `SpaAppointmentTableSwapConstraintTimingTests`.
- **Parking one appointment mid-swap on a value that avoids the constraint, then moving both into place, was considered and rejected twice** — once as a placeholder table (`SpaAppointment.tableId` is `NOT NULL`, so "park at NULL" isn't available without a column change, and a sentinel table row risks surfacing in the ordinary POS Tables admin screen, which lists every table with no active/zone filter), and once as a transient `status = CANCELLED` (rejected: `status` is a fact about the appointment's real life, not a slot for an implementation detail to borrow — the same "reused a business field as a mechanism" debt this project already carries with `PAID`, and a landmine for whoever later attaches real behaviour, like a notification, to becoming `CANCELLED`).
- **What actually works:** V56 made both exclusion constraints `DEFERRABLE INITIALLY IMMEDIATE`. `swapTables` calls `SpaAppointmentRepository#deferOverlapConstraints` (`SET CONSTRAINTS ... DEFERRED`, scoped to that one transaction — every other write stays checked exactly as before), applies both appointments' `tableId` changes as two ordinary `saveAndFlush` calls (flushed explicitly, not left to Hibernate's own batching, so the two `UPDATE`s are guaranteed to reach Postgres in this exact order before the next step), then calls `restoreImmediateOverlapConstraints` (`SET CONSTRAINTS ... IMMEDIATE`) to force the deferred checks to run right there, inside the method, where a real conflict still surfaces as a catchable `DataAccessException` — not silently pushed all the way to the transaction's own `COMMIT`, after the method has already returned. Proven correct (both the success and the still-genuinely-conflicting case) in `SpaAppointmentTableSwapDeferredConstraintTests`, written and passing *before* `swapTables` was changed to depend on it.
- **Why forcing the check back to immediate matters, specifically:** `AuditLogService.record` runs `REQUIRES_NEW` and commits independently and immediately (see the Tests section below) — an audit entry written before the deferred check is known to pass would survive a later rollback at `COMMIT`, permanently recording a swap that never happened. `swapTables` only calls `record` after `restoreImmediateOverlapConstraints` has already returned successfully.

**New bookings have limits (`BookingService`).** A stay is at most 90 nights (`MAX_NEW_STAY_NIGHTS`) on the public and staff create paths - not for a SiteMinder import (the guest already agreed it) or when extending a stay later. The public `POST /bookings` also refuses a check-in in the past and a party (adults + children) over `Room.capacity`. Staff are more trusted, not less careful: a booking that starts before today is back-entry and needs MANAGER+ (403 otherwise), and an over-capacity party is accepted with `Booking.warning` set (an extra bed is real). Tests that need a stay that already started create it as staff, not through the public form.

## Availability model

`Room` is a room *type*. `RoomUnit` is a physical room. A booking has segments (`BookingSegment`), one per room it occupies, covering the stay without gaps or overlaps — a booking with no relocation is one segment, not a special case.

Occupancy (`checkIn <= date < checkOut`) — the departure day is free. Back-to-back bookings on turnover day are valid.

`isActive = false` (permanently out of service) and `RoomUnitBlock` (temporarily out of sale, with dates and a reason) are **independent facts**. A blocked room is still active. Never collapse them into one "unavailable".

Occupancy state (checked in / departed) is a separate axis from booking status and does **not** affect availability - with one exception, below.

**A guest still `CHECKED_IN` after their `checkOut` date is in the house and holds their room through tonight - `OverstayRule` is the only definition of this.** "Who is in the house" used to have two answers that disagreed on exactly this guest: the Today board and property map read `occupancyStatus`, while availability, the calendar, the in-house list and `GET /bookings?from&to` (behind POS charge-to-room and the spa's guest picker) read the agreed dates. So a month-overdue guest was on the Today board but invisible everywhere else - their room was sold again, they couldn't be charged, and only the night audit said "N days overdue". The overstay is derived, never written: the nights `[checkOut, today]` in the room of the last segment, with no segment row, no rate and no change to `checkOut`. Every reader of occupancy asks `OverstayRule` (`AvailabilityService`, `BookingCalendarService` - `CalendarBooking.overstayUntil`, `BookingWriter`'s range and unit checks inside the SERIALIZABLE transaction, `ReportService#segmentsInRange` as a zero-revenue slice - the one population behind every room report, so In house, the manager report, occupancy/top production/market segment and the forecast all count the same guest, the Today board's departing list, `BookingService#list`, the spa's out-of-stay warning). The reports used to count agreed segment nights only, so the manager report said "0 occupied, 0 guests in house" on a night In house listed an overdue guest; occupancy now includes the overstay, revenue doesn't. Overdue starts the day *after* `checkOut`: on the departure day the guest is due out and that night stays sellable. The ways out are the existing ones - check-out, or extending the stay through `PATCH /bookings/{id}/schedule` (which prices the extra nights). Don't add a new reader of occupancy without asking `OverstayRule`.

`NightAuditBooking.unpaidOverstayNights` (shown on the night audit's missed departures as "Staying unpaid · N nights") is this same rule counted for the reviewed date: the nights `[checkOut, date]` inclusive - one more than the "N days overdue" beside it - and 0 for a guest due out that day, for anyone not `CHECKED_IN`, and on every other list. A warning only; `NightAuditService#unpaidOverstayNights`.

**A relocated booking's room can still be changed without changing dates.** `BookingWriter#assignRoomUnit`/`unassignRoomUnit` only ever operate on a booking's *sole* segment — convenient shorthand for the common never-relocated case — and reject once a booking has more than one segment. For a long time that rejection was the whole story: the only way to touch a relocated booking's room was `relocate`/`undo-relocation`, both of which also move dates. It no longer is. `reassignSegmentRoomUnit`/`unassignSegmentRoomUnit` (`PUT /bookings/{id}/segments/{segmentId}/room-unit`) are the general primitive underneath the whole-booking pair — same three checks (room type, active, free for that segment's own dates), same SERIALIZABLE race-safety, addressed at a named segment instead of implicitly "the sole segment." `swapSegmentRoomUnits` (`POST .../swap-room-unit`) builds on that for the one case a single segment-scoped call can't express: exchanging two bookings' rooms atomically, because two sequential single-segment calls would let the second call see the first guest's segment still occupying the room it's moving into. Two segments already in the *same* unit are a 400 too ("nothing to swap") - the calendar used to offer a "101 -> 101" swap when a bar was dropped on a neighbour in its own room, and confirming it wrote "Swapped rooms" into both histories (those old entries stay: the audit log is immutable). Same room type only, checked before any availability work (a 400, not a 409) — a cross-type swap would mean either retroactive repricing or a guest paying the other room's frozen rate, neither of which this API does silently. Treat any comment or description that still frames a relocated booking's room as fixed-until-undo as describing the *whole-booking shorthand* only, not a ceiling on what's possible.

The availability engine has been rewritten three times. Keep changes out of it unless the task is about it.

**A room type's name and a physical room's label are unique ignoring case, spaces at either end and the width of a run of spaces inside** ("Standard   Room" = "standard room", "Q1" = "q1"): `Room_name_normalized_key` and `RoomUnit_label_normalized_key` (V143) index `sunset_normalize_name(...)`, a SQL function that the services' `existsByNormalized...` queries call too, so the check and the index can't disagree; `RoomService`/`RoomUnitService` check first and answer 409, the index holds under a race, recognised by SQLSTATE 23505. V138/V143 never fail on old data: with duplicates they create no index and log one WARNING per group (DEPLOY.md has the check and the statement to run afterwards). **A `\v` in a Postgres `E'...'` string is the letter `v`, not a vertical tab** - V143's first version collapsed every "v" to a space; write `\u000b`. That is why `SiteMinderImportService`'s "more than one room type" guard stays, and why its test drops the index for its own duration.

## Authorization

Hierarchy: `ADMIN > MANAGER > CASHIER > WAITER`. `/users/**` is `ADMIN` only and deliberately outside the hierarchy.

**Every path in `openapi.yaml` needs an explicit rule in `SecurityConfig`.** `EndpointCoverageTests` reflects into the built filter chain and fails if any path falls through to `anyRequest()`. Order matters: specific matchers before general ones.

**Compare roles with explicit constants, never `ordinal()`.** `Role` is generated from `openapi.yaml`; reordering values there would silently invert an ordinal comparison.

**If a role may perform an action, it must be able to read the data that action requires.** This asymmetry has been introduced and fixed three times — a cashier allowed to assign a room but not to list rooms, and so on.

**Job functions are a second, independent authorization axis — not a fifth role.** `JobFunction` (`User.jobFunctions`, a set — see the Migrations section for why it's `TEXT[]`, not a native enum array) marks what a person can be assigned as (ENGINEER, HOUSEKEEPER, THERAPIST), not how much they can authorize. A role is one value on a strict ladder where each tier inherits everything below it; a function is a set a user can hold none, one, or several of, unrelated to seniority — a WAITER can also hold ENGINEER without that granting anything role-hierarchy-wide, and conversely a MANAGER can stand in for an engineer-gated action without ever holding the function (`SecurityConfig#engineerOrManagerPlus`). Folding a function into the role ladder would either grant privilege it shouldn't (inheriting up the hierarchy along with it) or force one skill per role tier, neither of which matches how a small hotel actually staffs. `JwtAuthFilter` grants each held function as its own `FUNCTION_<NAME>` authority; gate a path on one with `hasAuthority("FUNCTION_...")`, never `hasRole()`/`hasAnyRole()`, which would route it through the hierarchy and let it inherit along the role ladder. HOUSEKEEPER gates nothing. ENGINEER and THERAPIST each open one path: ENGINEER progresses a maintenance task (a MANAGER is an explicit fallback, not an implied one), THERAPIST **reads** the spa schedule (`GET /spa-appointments`, `/spa-appointments/therapists`) whatever the role (`SecurityConfig#cashierPlusOrTherapist`, owner's decision) — every spa write, the spa map and billing stay CASHIER+, and the function is still also who can be assigned as a therapist.

**A machine caller authenticates with its own scoped credential, never a staff login** — see `IntegrationKeyAuthFilter` (SiteMinder import section above).

Tokens carry a version. Changing a role, resetting a password, or disabling an account invalidates existing tokens immediately; `JwtAuthFilter` re-reads the user on every request. This is deliberate: without it a departing employee keeps access for a week.

## Audit log

**`AuditLogService.record()` needs a real `StaffPrincipal` in the security context - a background job cannot call it directly.** It fails open (see its own class javadoc) by catching everything and logging an error, so calling it from a job with no authenticated principal doesn't throw, it just silently records nothing. `AuditLogService.recordSystemAction(AuditAction, AuditEntityType, String, String)` is the overload for exactly that case - it skips `SecurityContextHolder` entirely. `AuditLogEntity.actorRole` is nullable now (`V100`, `DROP NOT NULL`) specifically to mark a system-initiated row; `actorUserId`/`actorEmail` stay `NOT NULL` and take plain-text sentinels (`"SYSTEM"` / `"system@sunsetbeach.internal"`) rather than a schema change, since they're already free-text columns. `BookingExpiryService`'s auto-cancellation sweep is the one caller so far, reusing `AuditAction.BOOKING_STATUS_CHANGED` - the same action a human cancellation uses. Deliberately not a `Role.SYSTEM` enum value: `Role` drives the auth hierarchy (`hasRole()`, every exhaustive role switch/dropdown in both repos), and polluting it for an audit-only distinction would mean auditing every one of those call sites to exclude it as an assignable staff role for no real gain.

**A new mutating service needs an explicit audit check, not an assumption it's covered.** `AttendanceDeviceService` and `MenuService` had zero audit coverage for their full CRUD lifecycle until this was caught by walking every DB-writing service against `AuditAction`/`AuditEntityType` by hand - there's no automated check that a new `@Transactional` write method calls `auditLogService.record(...)`, the way `EndpointCoverageTests` guarantees every `openapi.yaml` path has a `SecurityConfig` rule. When adding a new mutating service, follow `RoomUnitService`'s `ROOM_UNIT_CREATED`/`_UPDATED`/`_DELETED` shape as the closest working precedent instead of assuming CRUD-on-an-admin-entity is exempt.

## Failure handling

**Printing, email and audit writes must never break the operation they accompany.** An unreachable printer does not stop an order from being created or a shift from closing; the job is queued and retried. Audit records are written in their own transaction so a failure there cannot poison the main one.

**Periodic background work against something that can just be offline is a `@Scheduled` fixed-delay sweep, not a job queue with its own retry/backoff state.** `PrintService#retryPendingJobs` (PENDING print jobs), `BookingExpiryService#sweepUnconfirmedPublicBookings` (unconfirmed public bookings), and `AttendanceDevicePollService#pollDevices` (fingerprint terminals) are the same shape three times over: a plain `@Service` method, `@Scheduled(fixedDelayString = "${app.xxx.interval-ms:default}")`, iterating a small filtered query, each item's own failure caught and logged without stopping the rest of the sweep. `SunsetApplication`'s `@EnableScheduling` is what all three depend on — don't introduce `TaskScheduler`/`ScheduledExecutorService`/Quartz for a fourth one; this shape has covered every periodic-background-work need so far. `LifecycleEmailService#runDailySweep` is the same shape with a `cron` instead of a fixed delay (daily, 10:00 Asia/Bangkok) - a fixed delay would fire at whatever hour the server last started, and guest email should land at a sane hour. A failure in one unit of work (an unreachable printer, an unreachable terminal) is expected, not exceptional — log it and move on to the next item, never raise it as something a person has to dismiss.

**A device this system only ever polls, never accepts a connection from, needs no inbound endpoint and no auth story for one.** `AttendanceDevicePollService` reaches out to a fingerprint terminal on the hotel's own LAN; the terminal never calls in. This is a deliberate security property, not an incidental one: there is nothing for an attacker anywhere outside that LAN to reach, and nothing this API needs to authenticate a device *as*, because a device is never a caller. The one thing this buys nothing for is trust *in* the data — see `AttendanceService#ingestDevicePunch`'s own idempotent-ingestion contract, which the poll relies on regardless of which direction the connection runs.

**Idempotent ingestion covers a resent record, not a wrong one - the device's own claimed punch direction turned out to be exactly that.** `ZkTerminalClientImpl#directionOf` mapped the terminal's raw per-record "punch" byte to IN/OUT on an unverified guess (0=IN, 1=OUT), flagged in its own javadoc as needing confirmation against real hardware. Once a real K60 was connected, it turned out not to be trustworthy - a run of same-employee scans came back labelled IN three times in a row. `AttendanceService#ingestDevicePunch` no longer uses the device's reported direction to decide IN/OUT at all: it computes direction from that employee's own same-day punch count so far (even prior count -> IN, odd -> OUT - the same alternation `AttendancePunchPairing` and `recordPunch`'s `closesAnIncompleteDay` already assumed elsewhere), and only logs the device's claim as a WARN when it disagrees, as an ongoing diagnostic rather than ever trusting it. A record whose raw code doesn't even parse to a known value is no longer dropped either - it's accepted with a null diagnostic direction, since direction no longer depends on decoding it. A short debounce window (`app.attendance.punch-debounce-minutes`, default 2) also treats a same-employee scan too soon after the last one as an accidental double-tap and doesn't insert a second row for it - under history-based parity, a stray duplicate scan would otherwise flip every later punch's direction for the rest of that day, which is worse than what the old byte-trusting logic did.

**A poll windows from the last watermark with a fixed overlap, not a full re-read, once one exists.** `AttendanceDevicePollService` reads a device's entire log only when there's no watermark to window from yet — the first poll of a brand-new device, or a manual resync (`POST /attendance/devices/{id}/resync`). Every poll after that reads from an hour before the newest punch already ingested (`WATERMARK_OVERLAP`) to now, via the device's own `CMD_ATTLOG_TIME_RRQ` command — see `ZkTerminalClientImpl`'s own javadoc for where that command comes from and what happens when a device's firmware doesn't support it (a same-call fallback to a full read, not a poll failure). The overlap is what makes the window safe without a client-side watermark ever needing to be exact: Phase 1's idempotent ingestion absorbs anything it re-reads as a harmless `DUPLICATE`. What it does *not* cover is a device whose clock has jumped backward hard enough that new records now land before the watermark rather than after it (a factory reset, most plausibly) — `lastSeenAt` keeps updating normally through that, since it records when *we* successfully polled, not what the device's clock said, so this failure mode doesn't self-report. It's a case for an operator to notice and fix with a manual resync, not something the sweep is designed to detect on its own.

Front-desk operations warn rather than block. Checking a guest into an uncleaned room, or checking out with an outstanding balance, is allowed with a visible warning — a person stands at the desk and the system is not the one deciding.

A maintenance task's block is only ever **shortened** when the task is closed (`MaintenanceTaskService#liftBlock`): the new `toDate` is `min(current toDate, yesterday)`, and the block is deleted when that falls before its `fromDate`. Plain "yesterday" turned a block that had already expired (5-9 Oct), closed on the 11th, into 5-10 Oct and took the room off sale for a night that had been sellable.

The same rule covers blocking a room out of service (`RoomUnitService#createBlock`): a block is created even when it overlaps an existing booking, with a warning listing the affected booking(s) instead of a rejection. A burst pipe or a broken air conditioner is a fact about the room, not a request the software gets to veto because a reservation disagrees — refusing the block would leave staff unable to record what's actually true about the property, and would not fix the pipe. The warning exists so nobody unknowingly checks a guest into the affected room, or forgets to move one already there; deciding what to do about that guest stays a front-desk judgment call, same as everywhere else this rule applies.

## Dates

Dates of stay are date-only strings (`YYYY-MM-DD`) everywhere in the API. Timestamps (`createdAt`, `paidAt`, …) stay date-time. `DateOnlyFieldsContractTests` walks real responses and fails if a stay date acquires a time component — mixing the two formats previously caused the dashboard to report zero revenue for months.

## Clock and time zones

**Anything that reads "now" must go through the injected `Clock` bean — never a bare `LocalDateTime.now()`/`LocalDate.now()`.** `ClockConfig` used to be `Clock.systemDefaultZone()`, and nothing anywhere set `TZ` (checked `Dockerfile`/`docker-compose*.yml`/`.env*` — none), so it ran in the container's default zone: almost certainly UTC, seven hours off this hotel's real zone (Asia/Bangkok, UTC+7). It's now `Clock.system(ZoneId.of("Asia/Bangkok"))` — explicit, not dependent on the container ever having `TZ` set correctly. This bug shipped and stayed live for a stretch before it was caught, because "today" being wrong only shows up for part of the day (roughly 00:00-06:59 Bangkok time), not as an obvious constant failure.

**A class that keeps its own time source instead of taking the shared `Clock` will silently reintroduce this exact bug.** `ZkTerminalClientImpl` (the attendance terminal client) called a bare `LocalDateTime.now()` to both set the device's own clock (`CMD_SET_TIME`) and bound a windowed log read - completely independent of `ClockConfig`'s fix, because it built itself with a no-arg constructor instead of taking `Clock` as a dependency. The symptom was the terminal's own displayed time drifting back to wrong every ~5 minutes (one poll cycle), no matter how many times someone corrected it by hand on the device. Any new class that touches wall-clock time takes `Clock` as a constructor dependency, full stop - `grep -rn "LocalDateTime.now()\|LocalDate.now()\|LocalTime.now()"` (no `(clock)` argument) periodically to catch one that slipped through.

**Every timestamp column holds UTC wall-clock, and nothing may get it from the JVM default zone.** Use `@UtcCreationTimestamp`/`@UtcUpdateTimestamp`, never Hibernate's `@CreationTimestamp`/`@UpdateTimestamp`: for a `LocalDateTime` those read `Clock.systemDefaultZone()` (captured once, when Hibernate's `ClockHelper` loads), so a backend started on a Europe/Moscow machine wrote every new `createdAt` three hours ahead, with every test green because CI and production run in UTC. In service code, a value written to or compared against a timestamp column is `TimestampFormat.nowUtc(clock)`; "today" for stay/roster/block dates is `LocalDate.now(clock)` (hotel zone). `UtcTimestampDefaultZoneTests` runs the write paths under a Moscow default zone and fails if any entity uses Hibernate's annotations again.

**A "day" in any money or history query is a Bangkok day, converted to UTC for the comparison.** `createdAt`/`paidAt` columns hold UTC, so `LocalDate.atStartOfDay()` against them cuts the day at 07:00 Bangkok: a payment at 02:00 Bangkok (19:00 UTC the day before) fell into yesterday in `GET /payments/summary` - including its `folioPaymentsTotal`, the dashboard's "Room payments collected" - and in the orders list's date filters. `ReportDateRange#startUtc/endUtcExclusive(clock.getZone())` is the conversion for the report endpoints, the revenue export and `PaymentService`; `HotelDay#startUtc(day, zone)` is the same for the date filters of the orders list, the shift list and the audit log. A new date filter over a timestamp column uses one of them - never `atStartOfDay()` on its own. Tests write the boundary as a Bangkok time and convert (`PaymentsSummaryTests#bangkok`).

**`TimestampFormat.toUtc(LocalDateTime)` labels, it does not convert.** It's `value.atOffset(ZoneOffset.UTC)` - literally just stamps whatever wall-clock numbers it's handed as UTC. That's correct for its intended inputs: an `@UtcCreationTimestamp`/`@UtcUpdateTimestamp` field, or a value from `TimestampFormat.nowUtc(clock)`. It is silently wrong for any value built from `LocalDate.now(clock)`/`LocalDateTime.now(clock)` once that clock is Bangkok-zoned - `AttendanceService#toTodayShiftStatus`'s `referenceTime` was the one real call site that did this, producing attendance-lateness figures exactly seven hours short of the truth. The fix at a hotel-clock-derived value is `value.atZone(clock.getZone()).toOffsetDateTime()`, never `TimestampFormat.toUtc(value)` - that utility stays correct for its actual job; this was a wrong-function-at-one-call-site bug, not a bug in the utility. Before reusing `toUtc()` anywhere new, ask whether the `LocalDateTime` going in is already-UTC (`@UtcCreationTimestamp`/`nowUtc`) or hotel-clock-derived (needs the zone conversion instead).

**`AttendancePunchEntity.punchAt` is Asia/Bangkok wall-clock, not UTC - it counts as "clock-derived" for the rule above.** A scanner punch is the terminal's own clock reading (kept in Bangkok time by `setClock`), and every consumer groups and compares it as hotel-local: the today board's `today.atStartOfDay()` window, ingestion's same-day debounce and IN/OUT parity, the monthly summary, and the export's lateness sheet all compare `punchAt.toLocalDate()`/`toLocalTime()` against roster dates and shift times. The first fix for the lateness bug (`21b7656`) assumed the opposite, converted only the interval-derived `referenceTime` branches, and left the punch-derived ones (ON_SHIFT, FINISHED) seven hours in the future, which froze the admin board's live duration at "(0m)". A later brief proposed converting scanner punches to UTC at ingestion; that would have broken every consumer listed above. The fix that shipped goes the other way. `referenceTime` and the punch DTO's `punchAt` are zoned once on the way out (`atZone(clock.getZone()).toOffsetDateTime()`, a real `+07:00`). `recordPunch` converts its incoming `OffsetDateTime` into the clock's zone instead of keeping the digits of whatever offset it arrived with (the frontend sends UTC `Z`). `V101` shifted the MANUAL rows written before that fix by +7h.

## Tests

Testcontainers, one PostgreSQL container shared across the suite. The schema is loaded from the committed baseline dump, then Flyway applies anything newer.

Write tests for the thing that would silently produce a wrong number, not for framework plumbing. Concurrency claims need a real race (`CyclicBarrier` + `ExecutorService`, no `@Transactional` on the class) — a test that cannot observe the race proves nothing.

**`AuditLogService.record()` runs `REQUIRES_NEW` and swallows its own exceptions** (deliberate — see its class javadoc), reading the acting user from `SecurityContextHolder` rather than a parameter. In a test this means: no stubbed security context silently produces no audit row instead of a failure, and because it's a separate transaction, its writes commit and survive even when the surrounding `@Transactional` test method rolls back — clean up any rows it wrote in `@AfterEach`.

**A test must not read the wall clock — it builds its times from a fixed `Clock`.** `LocalDate.now()`/`LocalDateTime.now()`/an offset off either (`.minusMinutes(...)`, `.plusHours(...)`) makes a test's pass/fail depend on what real instant it happens to run at — most dangerously near local midnight, where an offset silently rolls onto the wrong calendar date for a few hours and the test only fails during that window. This shape has now appeared three times: `SpaMapServiceTests` (twice — see that class's own javadoc for the first, root-caused as a test bug, not a production one), and `OrderSpaAppointmentLinkTests`' two link-assertion tests, fixed the same way rather than with another one-off local helper (its `todayAt` predates this rule and was the second, narrower answer to the same problem — a fixed hour:minute on the real date, which only helps when the code under test never itself reads the wall clock; `SpaMapService`/`OrderService` both do, so a fixed `Clock` was the only fix that actually covers what those tests exercise). Where the code under test takes an injectable `Clock` (`SpaMapService`), override that bean with a fixed one, `@Primary`, in a nested `@TestConfiguration`. Where it instead reads a `@UtcCreationTimestamp`-generated field (`Order.createdAt`, `Booking.createdAt`, …) — Hibernate assigns those from the real clock at insert time, not from any injectable bean — build the test's own times from a fixed `Clock` and backdate the persisted row to that same instant with a native `UPDATE` plus `entityManager.clear()` (see `BookingExpiryServiceTests#persistBooking` and `OrderSpaAppointmentLinkTests#backdateOrderCreatedAt`); mutating the managed field directly is not picked up by dirty checking for a generated property, and skipping the `clear()` returns the stale cached value on the next read instead of the backdated row.

Run the whole suite, not only new classes.

## Naming

**"Shift" means a cash shift, and only a cash shift — never reuse it for the staff module's work-schedule concept.** `Shift`/`ShiftEntity`/`ShiftService` and everything else under that name is a cashier's session at a till: opened with a cash float, closed by counting the drawer, reconciled against `Payment` rows. The staff module (planned, not yet built) needs two other concepts, and they get their own words, reserved now so nobody reaches for "Shift" once that module is underway and has to invent a name under pressure:
- **"Roster"** for the planned schedule — who is due to work when.
- **"Attendance"** for what actually happened — clock in, clock out, hours worked.

These are deliberately two different words, not "roster" for both a plan and its own record: the whole point of that module is comparing what was planned against what happened, and one word for both would make that comparison unsayable — there'd be no way to ask "does the roster match attendance" without the question answering itself by definition. Keeping all three words - shift, roster, attendance - apart is what keeps that comparison a real question with a real answer, instead of a tautology.

## Attendance corrections

**A punch is never edited or deleted - a correction voids it.** `PUT /attendance/day` (`AttendanceService#correctDay`) replaces one employee's one hotel-local day: every live punch is flagged voided (`voidedAt`, `voidedByUserId`, `voidReason`, `voidedByCorrectionId`, V134) and the new times are recorded as `MANUAL` punches sharing a `correctionId`. The void is the only mutation a punch row ever gets, so a mistake - or tampering - leaves the earlier record behind. A day's versions stay clean sets (what a correction replaced / what it recorded), which is why the whole day is voided and re-recorded even when one time changed, and why rolling back is just another correction sending the earlier times.

**Every reader of punches asks for the live ones** (`...AndVoidedAtIsNull...` repository methods): summary, today board, the actuals export, recordPunch's parity count and the scanner's direction/debounce checks. Only `GET /attendance?includeVoided=true` (the history view) reads the unfiltered `findByEmployeeUserIdAndPunchAtBetweenOrderByPunchAt`. The scanner idempotency check (`existsByDeviceIdAndEnrollmentNumberAndPunchAt`) and the watermark deliberately still see voided rows - otherwise the next poll would re-ingest a punch someone had just corrected away.

**The correction takes `HH:mm` hotel times and a date, never an instant.** The server combines them (the manager's device zone can't matter), and directions are derived (IN, OUT, IN, ...) rather than trusted from the caller, the same positional rule `AttendancePunchPairing` reads by. A reason is required.

## Roster schedule import

`RosterImportService` reads the hotel's own hand-built Excel schedule (one sheet per month, named like `Sep26`) and turns it into `RosterEntry` rows - `POST /roster/import/preview` is a dry run (parses and resolves, writes nothing, not even a mapping), `POST /roster/import/name-mappings` and `.../color-mappings` are the only calls that record a mapping, `POST /roster/import/commit` is the only one that writes entries. ADMIN only - stricter than the rest of Roster's MANAGER floor, because it can create `User` accounts, the one thing `/users/**` itself is also hard-restricted to ADMIN for.

**Only the grid of codes is read.** `ScheduleWorkbookParser` locates the day-number header and the department/person rows by scanning forward from a known starting point until it recognises a stopping label ("Inhouse", "Total staffs", …) - never by counting columns from either end of the sheet. The trailing columns after the last day column shift position between months (one month even has an extra one the others don't, confirmed against the hotel's real four-month file), and the legend/totals/notes blocks sit past that stopping label - none of it is ever visited, regardless of what it contains.

**"9" is resolved by fill colour, and the colour-to-code-text mapping is remembered, not hardcoded - and it is not scoped by area.** Two different shifts are both written as the bare text "9" - yellow (a single 09:00-18:00 shift) or light blue (split), per `ShiftCodeService`'s own javadoc. `ShiftCode` has no colour concept, and two rows can never share `(staffArea, code)` at once (V57's own unique index), so whichever `ShiftCode` the "other" colour of "9" means necessarily has a *different* `code` string that can't be known ahead of time. `RosterImportShiftColorMapping` remembers that resulting code string (not a `ShiftCode` id, so a later version bump - V57's own versioning - doesn't silently invalidate the mapping) keyed only by `(rawCode, fillColor)`, resolved once via `POST /roster/import/color-mappings`, which validates at that moment - not later, on every future resolution - that the chosen `ShiftCode`'s own shape (one interval or two) actually matches what the colour means. A "9" whose fill matches neither yellow nor light blue is a fatal parse issue, reported and never guessed at.

Area was in this key for one round of this feature's life (V78) and it was a mistake, corrected in V81 - worth stating plainly since the reasoning that produced it looks plausible on the way in. Real data shows Kitchen uses *both* colours for "9" in the same month, which proves department never *determines* which colour is meant - but that's a fact about the grid, not about what the memory needs to key on. Which actual `ShiftCode` row a resolved code string points to *is* resolved per area, separately, at read time (`ShiftCodeService#resolveActive(staffArea, code)`, fed the cell's own area, called after the colour mapping has already answered "which code text") - conflating that already-area-aware lookup with the colour-to-text mapping itself is what produced the wrong key. The hotel's own legend lists exactly two "9" entries, not one pair per department, and the accountant who set the codes up confirmed it directly: colour separates the two shifts everywhere, not per area. One mapping now resolves "9" for every department that uses that colour, the same way a name is mapped once and works for every month after.

**Comments are never read, including "do not move".** `RosterEntry#locked`'s own openapi.yaml description already calls itself "the system-recognized form of 'do not move' - already written by hand as a cell comment in the spreadsheet this module replaces," which looks like an invitation to wire the two together. Read against the hotel's own real file first: every "do not move" comment found sits on a *blank* (day-off) cell, not a coded one - and a day off has no `RosterEntry` for a lock to attach to at all (see that entity's own "absence of a row" convention). There is no reliable, general cell-to-entry mapping to be found here, so none is attempted, for any comment - not just the ones that would have been hard, since acting on some and silently dropping others is its own kind of guess.

**Copying a month (`POST /roster/copy`) is by weekday, not by day of the month.** It's the way to set up a month nobody has an `EmployeePattern` for. The source (default: the whole previous month) is cut to whole weeks and repeated, so a weekly day off stays on its weekday; existing entries are never overwritten, inactive employees are skipped, and each copied entry is re-pointed to the `ShiftCode` version in force on its new date.

**The on-screen grid lists the same people the exports do** (`RosterService#listEmployeesForMonth`): active employees plus anyone deactivated who has an entry or a live punch that month, flagged `active: false` so the screen can grey them out. `GET /roster/employees` stays active-only (it feeds pickers). The bookings CSV (`GET /bookings/export`) carries the assigned room unit and `Balance due` (the folio calculator's figure) and writes `Created at` in the hotel zone with its offset. The grid export hides the re-import id columns.

**Names are never matched automatically, and existing entries are never overwritten.** A name is mapped once, by a person, and remembered by `(trimmed, whitespace-collapsed)` spelling against the account from then on - never inferred across months or fuzzy-matched. A cell whose `(employee, date)` already has a `RosterEntry` is always skipped and reported as a collision, never overwritten; resolving one, if the imported value should actually win, means clearing or editing the existing entry by hand and re-running the import. This also makes commit safe to retry after a lost response - anything already written the first time just shows up as a collision the second time.

**A staged upload lives in memory, keyed by an opaque id `commit` re-parses from.** Preview stores the raw file bytes (not the parsed/resolved result - resolution is re-derived fresh every time, from whatever's mapped *now*) in a plain in-memory map, swept opportunistically rather than on a `@Scheduled` job - this is a once-a-month, few-minutes-long admin task, not something worth a fourth periodic sweep, and this app's own "single hotel, single instance" premise (see this file's own opening line) is what makes in-memory state safe to reach for here at all.

**On-the-spot account creation doesn't fabricate an `EmployeePattern`.** "An employee can exist without login credentials" (see `UserService#create`) is what makes creating one mid-import cheap - name only, role `WAITER` (the safest default for an account nobody explicitly picked a role for), no email/password. The department a name's row sits under is used purely to resolve that name's own shift codes during this import; it is not persisted as an `EmployeePattern`, because that record also needs `workDaysPerWeek`/`weeklyDayOff`, which one month of attendance doesn't reliably establish - a manager sets that up deliberately, later, via the existing `/employee-patterns` screen, if this person turns out to have a standing weekly pattern worth generating from.

**A shift is never assigned to a deactivated employee** - `RosterService#requireActiveEmployee` guards create, move, reassign (target) and swap, `generateMonth` skips their patterns, and both Excel imports refuse the whole commit before writing anything. Their earlier entries stay and can still be deleted. **The two exports list the same people** (`RosterExportService#exportEmployeeIds`): every active employee plus anyone, active or not, with an entry or a live punch in the month - so someone deactivated mid-month is in both files, and an active employee nobody scheduled is a row of zeros in the actuals file. The on-screen grid (`RosterService#listEmployees`) is still active-only.

## Roster grid re-import (export -> edit -> re-import)

Distinct from the legacy Excel schedule import above - this is round-tripping the roster *grid* itself (already-committed `RosterEntry` rows) out to Excel, letting a manager edit it there, and syncing the changes back, rather than parsing the hotel's original hand-built file.

**The export embeds its own machine-readable ground truth in a hidden sheet, rather than re-deriving meaning from rendered cell styling on re-import.** A `VERY_HIDDEN` companion sheet carries employee ids, full historical `ShiftCode` field serialization (including `displayColor`), and a positional per-cell `shiftCodeId` pointer, cross-checked against the cell's own code text on re-import to catch silent staleness (the file was exported, the underlying `ShiftCode` changed since, and re-importing it would otherwise silently apply a stale mapping). This replaced an earlier design that tried to resolve a re-imported cell by matching its code text alone, which reintroduces exactly the kind of ambiguity `RosterImportShiftColorMapping` already exists to solve for the legacy import.

**Sync is a diff, keyed on `(employeeUserId, date)`, never a wholesale replace.** A re-import only ever adds, changes, or removes the specific cells that actually differ from what's currently in the database - a per-cell locked conflict is reported, not overridden. Staleness (the export is older than a since-changed entry) is recomputed fresh at `commit()`, never trusted from whatever `preview()` found - `preview()` and `commit()` can be arbitrarily far apart in time, and re-deriving from the database at the moment of the real write is what makes that gap safe.

## Working style

Investigate before changing. Several bugs in this project were "fixed" in the wrong place because behaviour was assumed rather than read.

When a decision is a judgment call — a data model, a permission boundary, anything touching money — state the options and the recommendation and wait, rather than choosing silently.

Do not touch the public site (`/public/**`, guest booking flow) unless the task is about it.
