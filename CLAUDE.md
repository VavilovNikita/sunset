# CLAUDE.md — sunset (backend)

Backend for a small resort's PMS + restaurant POS. Java 21, Spring Boot, PostgreSQL, Flyway, contract-first via `openapi.yaml`. Single hotel, single instance, on a server physically in the hotel.

Rules below were learned from real bugs. Where one looks arbitrary, the reason is stated — read it before deciding to do otherwise.

---

## Code generation

`openapi.yaml` is the source of truth and is edited by hand. Regenerate only with `scripts/generate-api.sh` — it carries the exact flags the committed code was produced with and is idempotent (running it twice changes nothing).

**Some generated files are hand-maintained and will be silently clobbered by a blind copy.** `scripts/generate-api.sh` is the definitive list of what it skips or patches — check it before trusting this summary:
- `AuthApi` is never generated at all, so there's nothing to clobber: `login()` needs an `HttpServletRequest` the generated signature can't carry, and `register()` would collide with `registerUser()` as two handlers on one route.
- `AuthResponse`, `LoginRequest` are fully hand-written, not templated output — deliberately no `toString()` override, so a stray log line can never print a raw JWT or password.
- `DeleteRoomImageRequest` is deliberately missing `@NotNull` on `path` so a null `path` produces the documented plain `ErrorMessage` (via `RoomController`'s manual check) instead of the `ValidationError` shape `@Valid` would trigger.
- `BookingCreateInput`, `UserCreateInput` stay in the generated copy, but a `sed` step in the script reapplies `@Email(message = "Invalid email")` after every regeneration — openapi.yaml alone can't express a custom Bean Validation message.

PII redaction in `toString()` is not manual any more: mark a property `x-sensitive: true` in `openapi.yaml` and the template renders `[REDACTED]`. `ToStringRedactsGuestPiiTests` fails if this regresses.

**A `nullable: true` + `required` property in openapi.yaml generates a `@NotNull` that rejects the very null it's supposed to allow.** The codegen's `JsonNullable<T>` wrapper unwraps before Bean Validation sees it, so `@NotNull` validates the unwrapped value, not the wrapper. Fix by omitting the field from `required:` and validating manually in the service — don't add it back to `required:` to "match the schema."

## Migrations

**The schema cannot be built from migrations alone.** `V1` is an intentional no-op: the original tables were created by Prisma before this backend existed, and Flyway adopts that schema via `baseline-on-migrate`. Never drop the database expecting migrations to recreate it. Tests bootstrap from a committed baseline dump instead.

**`ALTER TYPE ... ADD VALUE` and any DML using the new value must be in separate migration files.** PostgreSQL forbids using a freshly added enum value in the same transaction, and Flyway wraps each migration in one. See V2/V3 (new `Role` values) and V6/V7 (new `PrintDocumentType` value, then a backfill — V6's own comment explains the split).

**A set of values on one row is `TEXT[]` plus a `CHECK` constraint, not a native Postgres enum array.** `Role` is a native enum (one value per row); `JobFunction` (`User.jobFunctions`, a set) is not, deliberately — this project has a working Hibernate mapping for a scalar native enum and for a plain array (`RoomEntity.images` is the only array column here, and it's `text[]`), but none for an *array of a custom enum type*, and `V33__user_job_functions.sql` wasn't the place to become the first. The `CHECK` constraint is the DB-side validation a native enum would otherwise provide. Don't "fix" this inconsistency by converting it to a native enum array — read `V33`'s own comment first. It's a deliberate trade-off, not an oversight: it costs `JobFunction` the type safety a native enum gets, but it buys a real simplification — adding a third value later is one migration updating the `CHECK` constraint, not the `ALTER TYPE`-plus-separate-migration dance the rule above describes.

Some migrations are destructive (dropped columns, deleted rows) — V4 and V11 are the two so far. Code rollback alone is not safe once one of these has run; restoring means restoring a dump. Take one before deploying.

## Money

**The server computes every amount. A client-supplied price or total is never trusted, ever.** This holds for room rates, order totals, payments, and folio balances.

**Agreed prices are frozen per night** (`BookingSegmentNightlyRate`). Extending a stay prices only the new nights; already-agreed nights keep their original rate. Repricing an existing night happens only through the explicit reprice action, and only for nights from today forward. This exists because the system used to recompute the whole stay from current rates, so extending a booking by one night silently repriced the entire stay.

Undoing a relocation restores the preserved original rates. It is not a new agreement.

## Spa billing

**What links a POS order to a spa appointment is presence, not a status.** `SpaAppointment.orderId` is set once — explicitly by the spa billing door (`POST /orders` with `spaAppointmentId`) or by `OrderService`'s own auto-link (by table, then by booking, tried at different moments — see `OrderService#autoLinkSpaAppointment`'s own javadoc) — and answers exactly one question: is this the order that bills this appointment's treatment. `Order.bookingId` is not the same fact and never was — see that field's own openapi.yaml description; the record of what a *closed* order was actually charged to is `Payment.bookingId`, set independently at `POST /orders/{id}/close`.

**Multi-treatment: a child row per treatment, no frozen price.** `SpaAppointmentTreatment` (`V50__spa_appointment_treatment.sql`) is one row per treatment on an appointment — the same treatment booked twice is two rows, not a quantity of two. `SpaAppointment.durationMinutes` stays a maintained sum over those rows (recomputed on every add/remove, never derived on the fly), specifically so both `EXCLUDE USING gist` constraints keep reading one plain column and never need to know the treatment table exists. `SpaAppointmentTreatment` freezes `durationMinutes` at add time (same "agreed terms are frozen" precedent as `BookingSegmentNightlyRate`) but deliberately **not price**: a room night bypasses the POS `OrderItem`/menu system entirely (`Payment.method=ROOM_CHARGE` reads `Booking.totalPrice` directly), so freezing there protects the only price authority that charge has. A spa treatment bills through the ordinary `OrderService#addItems`, which has exactly one pricing rule project-wide — read the menu live at the moment a line is added to an order. Freezing a second price on the appointment would manufacture a number that can silently disagree with the one actually charged, not protect a guest-facing quote (no price is shown when an appointment is booked). `SpaAppointmentTreatment.currentPrice` on the DTO is a live, unstored `MenuItem.price` read at response time — same "denormalized, not frozen" convention as `treatmentName` — shown for reception's own reference and never read by any billing path. Adding a treatment is legal only while `status` is `BOOKED` (growing `durationMinutes` can collide, same `translateOverlap` 409 handling as `create`); removing one is legal through `BOOKED` or `COMPLETED` (shrinking can never create a new overlap, so it never risks a 409) but always leaves at least one row — an appointment cannot exist with zero treatments. The old singular `SpaAppointment.treatmentMenuItemId` column stays on the table, unused by any code, until a full reader sweep clears it for `V53` to drop.

The billing *warning* is a separate question from the link, asked by the server, not by `OrderService`: `SpaAppointment.missingTreatmentNames` names which of this appointment's treatments the linked order doesn't (yet) carry, computed only once `status` is `COMPLETED` (empty for every other status, regardless of `orderId`) as a multiset comparison — for each `treatmentMenuItemId`, does the linked order's item quantity for it meet or exceed how many times this appointment booked it. **A `CANCELLED` linked order counts as carrying nothing of the appointment's treatments**, same as no order at all — a cancelled order keeps its items and keeps the link (nothing clears `orderId` on cancel), but it bills nothing, so treating its items as still-billing would let the warning go quiet on an appointment nobody actually charged. Presence still decides the *link*, completeness decides the *warning* — don't fold the two questions back into one gate. `SpaAppointmentService#getSchedule` (the day-grid read) computes this batched, not per-appointment: it only fetches order/order-item rows for appointments that are actually `COMPLETED` with a non-null `orderId`, via `OrderItemRepository#findByOrderIdIn`, so a day of mostly-`BOOKED` appointments costs nothing extra regardless of how many there are. The single-appointment write paths (`create`, `addTreatment`, `removeTreatment`, `updateStatus`, `updateSchedule`) share the same completeness computation (`SpaAppointmentService#computeMissingTreatmentNames`) fed per-appointment inputs instead — one method, two call shapes, so the batched and single-appointment reads can never silently diverge on what "missing" means.

## Concurrency

Availability writes run `SERIALIZABLE` in `BookingWriter`, and PostgreSQL serialization failures (SQLSTATE 40001) are translated to `ConflictException` with a human message. `BookingWriter` is a separate bean specifically so the `@Transactional` proxy applies — self-invocation would bypass it.

**Recognise a database failure by its SQLSTATE, never by message text.** Message wording isn't part of Postgres's own contract — it can vary by server/driver version and locale, and some failures don't name what they were checking when they landed at all. `SpaAppointmentService#translateOverlap` used to match the violated exclusion constraint's own name inside the exception's message; that works for a genuine overlap (the message does name the constraint) but is structurally blind to a deadlock (SQLSTATE `40P01`), whose own message names the *relation* it was checking a constraint on, never the constraint itself. A real, reachable deadlock between this service's own deferred-then-forced-immediate check (`swapTables`) and a concurrent ordinary write checking the same range escaped as a raw, untranslated 500 instead of the same "try again" conflict every other race in this system gives — found only because it fired once under load running the whole suite together, not from reading the code. Walk the cause chain for the actual `java.sql.SQLException` and compare `getSQLState()` instead (see `com.sunsetbeach.error.SqlStates`, shared by `BookingService#isSerializationFailure` for `40001` and `SpaAppointmentService#translateOverlap` for `23P01`/`40P01`) — never re-derive what kind of failure this is from prose that was never meant to be parsed.

Do not copy `SERIALIZABLE` to writes that do not contend for inventory. POS order and payment writes use ordinary transactions; using SERIALIZABLE there would produce spurious conflicts during service hours.

Where a race is better solved by the database, use the database. Three tools exist here for three different shapes of conflict, and picking the wrong one either misses real races or produces spurious ones:
- **SERIALIZABLE** (`BookingWriter`) — when availability itself has to be recomputed from several sources (unit counts, blocks, other segments) and can't be expressed as a single row-level constraint.
- **A unique constraint** — when the rule is "at most one," not "no two may overlap": one payment per order is enforced this way, not by a check-then-write.
- **A Postgres `EXCLUDE USING gist` constraint** — when the rule is "no two rows may overlap on a range," and the database can express that directly. The spa module uses one per axis (`spa_appointment_no_table_overlap`, `spa_appointment_no_therapist_overlap` — see `V41__spa_appointment.sql`/`V43__spa_appointment_completed_still_occupies_slot.sql`) instead of a pre-write query: `SpaAppointmentService` never checks for a conflict before writing, it writes directly and lets the constraint reject, translated to a human message by `translateOverlap` — by SQLSTATE first (see this section's own rule on recognising database failures), the constraint's own name only decides which of the two sentences to return. This is cheaper than SERIALIZABLE and correct here specifically because the check needs no unit-counting or block-checking — just "does this interval overlap that one" - which is exactly what the constraint already computes.

**Swapping two rows across an exclusion constraint needs the constraint deferred, not a clever statement.** `SpaAppointmentService#swapTables` (table-only: date/startTime/therapistUserId/durationMinutes never move on either side, which is what makes it well-defined regardless of how long either treatment runs) looks like it should be two ordinary `UPDATE`s — and three people in a row reasoned their way to an implementation that doesn't work before this one shipped. Read this before trying another:
- **A single statement moving both rows, against a `NOT DEFERRABLE` constraint, does not work.** The theory was that Postgres checks a constraint like this once, at the end of the statement — true for a `DEFERRABLE` constraint left `INITIALLY IMMEDIATE`, false for one that is not deferrable at all. `NOT DEFERRABLE` is enforced synchronously, per row, as each row's GiST index entry is written — so a single `UPDATE ... CASE id WHEN ...` moving both appointments still finds the other one sitting on its target table, regardless of row-processing order, whenever the two appointments' times actually overlap (the only case a swap is worth doing at all). Proven wrong in `SpaAppointmentTableSwapConstraintTimingTests`.
- **Parking one appointment mid-swap on a value that avoids the constraint, then moving both into place, was considered and rejected twice** — once as a placeholder table (`SpaAppointment.tableId` is `NOT NULL`, so "park at NULL" isn't available without a column change, and a sentinel table row risks surfacing in the ordinary POS Tables admin screen, which lists every table with no active/zone filter), and once as a transient `status = CANCELLED` (rejected: `status` is a fact about the appointment's real life, not a slot for an implementation detail to borrow — the same "reused a business field as a mechanism" debt this project already carries with `PAID`, and a landmine for whoever later attaches real behaviour, like a notification, to becoming `CANCELLED`).
- **What actually works:** V56 made both exclusion constraints `DEFERRABLE INITIALLY IMMEDIATE`. `swapTables` calls `SpaAppointmentRepository#deferOverlapConstraints` (`SET CONSTRAINTS ... DEFERRED`, scoped to that one transaction — every other write stays checked exactly as before), applies both appointments' `tableId` changes as two ordinary `saveAndFlush` calls (flushed explicitly, not left to Hibernate's own batching, so the two `UPDATE`s are guaranteed to reach Postgres in this exact order before the next step), then calls `restoreImmediateOverlapConstraints` (`SET CONSTRAINTS ... IMMEDIATE`) to force the deferred checks to run right there, inside the method, where a real conflict still surfaces as a catchable `DataAccessException` — not silently pushed all the way to the transaction's own `COMMIT`, after the method has already returned. Proven correct (both the success and the still-genuinely-conflicting case) in `SpaAppointmentTableSwapDeferredConstraintTests`, written and passing *before* `swapTables` was changed to depend on it.
- **Why forcing the check back to immediate matters, specifically:** `AuditLogService.record` runs `REQUIRES_NEW` and commits independently and immediately (see the Tests section below) — an audit entry written before the deferred check is known to pass would survive a later rollback at `COMMIT`, permanently recording a swap that never happened. `swapTables` only calls `record` after `restoreImmediateOverlapConstraints` has already returned successfully.

## Availability model

`Room` is a room *type*. `RoomUnit` is a physical room. A booking has segments (`BookingSegment`), one per room it occupies, covering the stay without gaps or overlaps — a booking with no relocation is one segment, not a special case.

Occupancy (`checkIn <= date < checkOut`) — the departure day is free. Back-to-back bookings on turnover day are valid.

`isActive = false` (permanently out of service) and `RoomUnitBlock` (temporarily out of sale, with dates and a reason) are **independent facts**. A blocked room is still active. Never collapse them into one "unavailable".

Occupancy state (checked in / departed) is a separate axis from booking status and does **not** affect availability.

**A relocated booking's room can still be changed without changing dates.** `BookingWriter#assignRoomUnit`/`unassignRoomUnit` only ever operate on a booking's *sole* segment — convenient shorthand for the common never-relocated case — and reject once a booking has more than one segment. For a long time that rejection was the whole story: the only way to touch a relocated booking's room was `relocate`/`undo-relocation`, both of which also move dates. It no longer is. `reassignSegmentRoomUnit`/`unassignSegmentRoomUnit` (`PUT /bookings/{id}/segments/{segmentId}/room-unit`) are the general primitive underneath the whole-booking pair — same three checks (room type, active, free for that segment's own dates), same SERIALIZABLE race-safety, addressed at a named segment instead of implicitly "the sole segment." `swapSegmentRoomUnits` (`POST .../swap-room-unit`) builds on that for the one case a single segment-scoped call can't express: exchanging two bookings' rooms atomically, because two sequential single-segment calls would let the second call see the first guest's segment still occupying the room it's moving into. Same room type only, checked before any availability work (a 400, not a 409) — a cross-type swap would mean either retroactive repricing or a guest paying the other room's frozen rate, neither of which this API does silently. Treat any comment or description that still frames a relocated booking's room as fixed-until-undo as describing the *whole-booking shorthand* only, not a ceiling on what's possible.

The availability engine has been rewritten three times. Keep changes out of it unless the task is about it.

## Authorization

Hierarchy: `ADMIN > MANAGER > CASHIER > WAITER`. `/users/**` is `ADMIN` only and deliberately outside the hierarchy.

**Every path in `openapi.yaml` needs an explicit rule in `SecurityConfig`.** `EndpointCoverageTests` reflects into the built filter chain and fails if any path falls through to `anyRequest()`. Order matters: specific matchers before general ones.

**Compare roles with explicit constants, never `ordinal()`.** `Role` is generated from `openapi.yaml`; reordering values there would silently invert an ordinal comparison.

**If a role may perform an action, it must be able to read the data that action requires.** This asymmetry has been introduced and fixed three times — a cashier allowed to assign a room but not to list rooms, and so on.

**Job functions are a second, independent authorization axis — not a fifth role.** `JobFunction` (`User.jobFunctions`, a set — see the Migrations section for why it's `TEXT[]`, not a native enum array) marks what a person can be assigned as (ENGINEER, HOUSEKEEPER, THERAPIST), not how much they can authorize. A role is one value on a strict ladder where each tier inherits everything below it; a function is a set a user can hold none, one, or several of, unrelated to seniority — a WAITER can also hold ENGINEER without that granting anything role-hierarchy-wide, and conversely a MANAGER can stand in for an engineer-gated action without ever holding the function (`SecurityConfig#engineerOrManagerPlus`). Folding a function into the role ladder would either grant privilege it shouldn't (inheriting up the hierarchy along with it) or force one skill per role tier, neither of which matches how a small hotel actually staffs. `JwtAuthFilter` grants each held function as its own `FUNCTION_<NAME>` authority; gate a path on one with `hasAuthority("FUNCTION_...")`, never `hasRole()`/`hasAnyRole()`, which would route it through the hierarchy and let it inherit along the role ladder. Most functions gate nothing at all today — THERAPIST and HOUSEKEEPER are pure domain-eligibility tags (who can be assigned as a spa therapist; nothing about permission) — ENGINEER is the one exception so far, and even there a MANAGER is an explicit fallback, not an implied one.

Tokens carry a version. Changing a role, resetting a password, or disabling an account invalidates existing tokens immediately; `JwtAuthFilter` re-reads the user on every request. This is deliberate: without it a departing employee keeps access for a week.

## Audit log

**`AuditLogService.record()` needs a real `StaffPrincipal` in the security context - a background job cannot call it directly.** It fails open (see its own class javadoc) by catching everything and logging an error, so calling it from a job with no authenticated principal doesn't throw, it just silently records nothing. `AuditLogService.recordSystemAction(AuditAction, AuditEntityType, String, String)` is the overload for exactly that case - it skips `SecurityContextHolder` entirely. `AuditLogEntity.actorRole` is nullable now (`V100`, `DROP NOT NULL`) specifically to mark a system-initiated row; `actorUserId`/`actorEmail` stay `NOT NULL` and take plain-text sentinels (`"SYSTEM"` / `"system@sunsetbeach.internal"`) rather than a schema change, since they're already free-text columns. `BookingExpiryService`'s auto-cancellation sweep is the one caller so far, reusing `AuditAction.BOOKING_STATUS_CHANGED` - the same action a human cancellation uses. Deliberately not a `Role.SYSTEM` enum value: `Role` drives the auth hierarchy (`hasRole()`, every exhaustive role switch/dropdown in both repos), and polluting it for an audit-only distinction would mean auditing every one of those call sites to exclude it as an assignable staff role for no real gain.

**A new mutating service needs an explicit audit check, not an assumption it's covered.** `AttendanceDeviceService` and `MenuService` had zero audit coverage for their full CRUD lifecycle until this was caught by walking every DB-writing service against `AuditAction`/`AuditEntityType` by hand - there's no automated check that a new `@Transactional` write method calls `auditLogService.record(...)`, the way `EndpointCoverageTests` guarantees every `openapi.yaml` path has a `SecurityConfig` rule. When adding a new mutating service, follow `RoomUnitService`'s `ROOM_UNIT_CREATED`/`_UPDATED`/`_DELETED` shape as the closest working precedent instead of assuming CRUD-on-an-admin-entity is exempt.

## Failure handling

**Printing, email and audit writes must never break the operation they accompany.** An unreachable printer does not stop an order from being created or a shift from closing; the job is queued and retried. Audit records are written in their own transaction so a failure there cannot poison the main one.

**Periodic background work against something that can just be offline is a `@Scheduled` fixed-delay sweep, not a job queue with its own retry/backoff state.** `PrintService#retryPendingJobs` (PENDING print jobs), `BookingExpiryService#sweepUnconfirmedPublicBookings` (unconfirmed public bookings), and `AttendanceDevicePollService#pollDevices` (fingerprint terminals) are the same shape three times over: a plain `@Service` method, `@Scheduled(fixedDelayString = "${app.xxx.interval-ms:default}")`, iterating a small filtered query, each item's own failure caught and logged without stopping the rest of the sweep. `SunsetApplication`'s `@EnableScheduling` is what all three depend on — don't introduce `TaskScheduler`/`ScheduledExecutorService`/Quartz for a fourth one; this shape has covered every periodic-background-work need so far. A failure in one unit of work (an unreachable printer, an unreachable terminal) is expected, not exceptional — log it and move on to the next item, never raise it as something a person has to dismiss.

**A device this system only ever polls, never accepts a connection from, needs no inbound endpoint and no auth story for one.** `AttendanceDevicePollService` reaches out to a fingerprint terminal on the hotel's own LAN; the terminal never calls in. This is a deliberate security property, not an incidental one: there is nothing for an attacker anywhere outside that LAN to reach, and nothing this API needs to authenticate a device *as*, because a device is never a caller. The one thing this buys nothing for is trust *in* the data — see `AttendanceService#ingestDevicePunch`'s own idempotent-ingestion contract, which the poll relies on regardless of which direction the connection runs.

**Idempotent ingestion covers a resent record, not a wrong one - the device's own claimed punch direction turned out to be exactly that.** `ZkTerminalClientImpl#directionOf` mapped the terminal's raw per-record "punch" byte to IN/OUT on an unverified guess (0=IN, 1=OUT), flagged in its own javadoc as needing confirmation against real hardware. Once a real K60 was connected, it turned out not to be trustworthy - a run of same-employee scans came back labelled IN three times in a row. `AttendanceService#ingestDevicePunch` no longer uses the device's reported direction to decide IN/OUT at all: it computes direction from that employee's own same-day punch count so far (even prior count -> IN, odd -> OUT - the same alternation `AttendancePunchPairing` and `recordPunch`'s `closesAnIncompleteDay` already assumed elsewhere), and only logs the device's claim as a WARN when it disagrees, as an ongoing diagnostic rather than ever trusting it. A record whose raw code doesn't even parse to a known value is no longer dropped either - it's accepted with a null diagnostic direction, since direction no longer depends on decoding it. A short debounce window (`app.attendance.punch-debounce-minutes`, default 2) also treats a same-employee scan too soon after the last one as an accidental double-tap and doesn't insert a second row for it - under history-based parity, a stray duplicate scan would otherwise flip every later punch's direction for the rest of that day, which is worse than what the old byte-trusting logic did.

**A poll windows from the last watermark with a fixed overlap, not a full re-read, once one exists.** `AttendanceDevicePollService` reads a device's entire log only when there's no watermark to window from yet — the first poll of a brand-new device, or a manual resync (`POST /attendance/devices/{id}/resync`). Every poll after that reads from an hour before the newest punch already ingested (`WATERMARK_OVERLAP`) to now, via the device's own `CMD_ATTLOG_TIME_RRQ` command — see `ZkTerminalClientImpl`'s own javadoc for where that command comes from and what happens when a device's firmware doesn't support it (a same-call fallback to a full read, not a poll failure). The overlap is what makes the window safe without a client-side watermark ever needing to be exact: Phase 1's idempotent ingestion absorbs anything it re-reads as a harmless `DUPLICATE`. What it does *not* cover is a device whose clock has jumped backward hard enough that new records now land before the watermark rather than after it (a factory reset, most plausibly) — `lastSeenAt` keeps updating normally through that, since it records when *we* successfully polled, not what the device's clock said, so this failure mode doesn't self-report. It's a case for an operator to notice and fix with a manual resync, not something the sweep is designed to detect on its own.

Front-desk operations warn rather than block. Checking a guest into an uncleaned room, or checking out with an outstanding balance, is allowed with a visible warning — a person stands at the desk and the system is not the one deciding.

The same rule covers blocking a room out of service (`RoomUnitService#createBlock`): a block is created even when it overlaps an existing booking, with a warning listing the affected booking(s) instead of a rejection. A burst pipe or a broken air conditioner is a fact about the room, not a request the software gets to veto because a reservation disagrees — refusing the block would leave staff unable to record what's actually true about the property, and would not fix the pipe. The warning exists so nobody unknowingly checks a guest into the affected room, or forgets to move one already there; deciding what to do about that guest stays a front-desk judgment call, same as everywhere else this rule applies.

## Dates

Dates of stay are date-only strings (`YYYY-MM-DD`) everywhere in the API. Timestamps (`createdAt`, `paidAt`, …) stay date-time. `DateOnlyFieldsContractTests` walks real responses and fails if a stay date acquires a time component — mixing the two formats previously caused the dashboard to report zero revenue for months.

## Clock and time zones

**Anything that reads "now" must go through the injected `Clock` bean — never a bare `LocalDateTime.now()`/`LocalDate.now()`.** `ClockConfig` used to be `Clock.systemDefaultZone()`, and nothing anywhere set `TZ` (checked `Dockerfile`/`docker-compose*.yml`/`.env*` — none), so it ran in the container's default zone: almost certainly UTC, seven hours off this hotel's real zone (Asia/Bangkok, UTC+7). It's now `Clock.system(ZoneId.of("Asia/Bangkok"))` — explicit, not dependent on the container ever having `TZ` set correctly. This bug shipped and stayed live for a stretch before it was caught, because "today" being wrong only shows up for part of the day (roughly 00:00-06:59 Bangkok time), not as an obvious constant failure.

**A class that keeps its own time source instead of taking the shared `Clock` will silently reintroduce this exact bug.** `ZkTerminalClientImpl` (the attendance terminal client) called a bare `LocalDateTime.now()` to both set the device's own clock (`CMD_SET_TIME`) and bound a windowed log read - completely independent of `ClockConfig`'s fix, because it built itself with a no-arg constructor instead of taking `Clock` as a dependency. The symptom was the terminal's own displayed time drifting back to wrong every ~5 minutes (one poll cycle), no matter how many times someone corrected it by hand on the device. Any new class that touches wall-clock time takes `Clock` as a constructor dependency, full stop - `grep -rn "LocalDateTime.now()\|LocalDate.now()\|LocalTime.now()"` (no `(clock)` argument) periodically to catch one that slipped through.

**`TimestampFormat.toUtc(LocalDateTime)` labels, it does not convert.** It's `value.atOffset(ZoneOffset.UTC)` - literally just stamps whatever wall-clock numbers it's handed as UTC. That's correct for its one intended input, a Hibernate `@CreationTimestamp`/`@UpdateTimestamp` field (Hibernate populates those from its own internal clock, genuinely UTC, unrelated to the app's `clock` bean). It is silently wrong for any value built from `LocalDate.now(clock)`/`LocalDateTime.now(clock)` once that clock is Bangkok-zoned - `AttendanceService#toTodayShiftStatus`'s `referenceTime` was the one real call site that did this, producing attendance-lateness figures exactly seven hours short of the truth. The fix at a clock-derived value is `value.atZone(clock.getZone()).toOffsetDateTime()`, never `TimestampFormat.toUtc(value)` - that utility stays correct for its actual job; this was a wrong-function-at-one-call-site bug, not a bug in the utility. Before reusing `toUtc()` anywhere new, ask whether the `LocalDateTime` going in is already-UTC (Hibernate-populated) or clock-derived (needs the zone conversion instead).

## Tests

Testcontainers, one PostgreSQL container shared across the suite. The schema is loaded from the committed baseline dump, then Flyway applies anything newer.

Write tests for the thing that would silently produce a wrong number, not for framework plumbing. Concurrency claims need a real race (`CyclicBarrier` + `ExecutorService`, no `@Transactional` on the class) — a test that cannot observe the race proves nothing.

**`AuditLogService.record()` runs `REQUIRES_NEW` and swallows its own exceptions** (deliberate — see its class javadoc), reading the acting user from `SecurityContextHolder` rather than a parameter. In a test this means: no stubbed security context silently produces no audit row instead of a failure, and because it's a separate transaction, its writes commit and survive even when the surrounding `@Transactional` test method rolls back — clean up any rows it wrote in `@AfterEach`.

**A test must not read the wall clock — it builds its times from a fixed `Clock`.** `LocalDate.now()`/`LocalDateTime.now()`/an offset off either (`.minusMinutes(...)`, `.plusHours(...)`) makes a test's pass/fail depend on what real instant it happens to run at — most dangerously near local midnight, where an offset silently rolls onto the wrong calendar date for a few hours and the test only fails during that window. This shape has now appeared three times: `SpaMapServiceTests` (twice — see that class's own javadoc for the first, root-caused as a test bug, not a production one), and `OrderSpaAppointmentLinkTests`' two link-assertion tests, fixed the same way rather than with another one-off local helper (its `todayAt` predates this rule and was the second, narrower answer to the same problem — a fixed hour:minute on the real date, which only helps when the code under test never itself reads the wall clock; `SpaMapService`/`OrderService` both do, so a fixed `Clock` was the only fix that actually covers what those tests exercise). Where the code under test takes an injectable `Clock` (`SpaMapService`), override that bean with a fixed one, `@Primary`, in a nested `@TestConfiguration`. Where it instead reads a `@CreationTimestamp`-generated field (`Order.createdAt`, `Booking.createdAt`, …) — Hibernate assigns those from the real clock at insert time, not from any injectable bean — build the test's own times from a fixed `Clock` and backdate the persisted row to that same instant with a native `UPDATE` plus `entityManager.clear()` (see `BookingExpiryServiceTests#persistBooking` and `OrderSpaAppointmentLinkTests#backdateOrderCreatedAt`); mutating the managed field directly is not picked up by dirty checking for a generated property, and skipping the `clear()` returns the stale cached value on the next read instead of the backdated row.

Run the whole suite, not only new classes.

## Naming

**"Shift" means a cash shift, and only a cash shift — never reuse it for the staff module's work-schedule concept.** `Shift`/`ShiftEntity`/`ShiftService` and everything else under that name is a cashier's session at a till: opened with a cash float, closed by counting the drawer, reconciled against `Payment` rows. The staff module (planned, not yet built) needs two other concepts, and they get their own words, reserved now so nobody reaches for "Shift" once that module is underway and has to invent a name under pressure:
- **"Roster"** for the planned schedule — who is due to work when.
- **"Attendance"** for what actually happened — clock in, clock out, hours worked.

These are deliberately two different words, not "roster" for both a plan and its own record: the whole point of that module is comparing what was planned against what happened, and one word for both would make that comparison unsayable — there'd be no way to ask "does the roster match attendance" without the question answering itself by definition. Keeping all three words - shift, roster, attendance - apart is what keeps that comparison a real question with a real answer, instead of a tautology.

## Roster schedule import

`RosterImportService` reads the hotel's own hand-built Excel schedule (one sheet per month, named like `Sep26`) and turns it into `RosterEntry` rows - `POST /roster/import/preview` is a dry run (parses and resolves, writes nothing, not even a mapping), `POST /roster/import/name-mappings` and `.../color-mappings` are the only calls that record a mapping, `POST /roster/import/commit` is the only one that writes entries. ADMIN only - stricter than the rest of Roster's MANAGER floor, because it can create `User` accounts, the one thing `/users/**` itself is also hard-restricted to ADMIN for.

**Only the grid of codes is read.** `ScheduleWorkbookParser` locates the day-number header and the department/person rows by scanning forward from a known starting point until it recognises a stopping label ("Inhouse", "Total staffs", …) - never by counting columns from either end of the sheet. The trailing columns after the last day column shift position between months (one month even has an extra one the others don't, confirmed against the hotel's real four-month file), and the legend/totals/notes blocks sit past that stopping label - none of it is ever visited, regardless of what it contains.

**"9" is resolved by fill colour, and the colour-to-code-text mapping is remembered, not hardcoded - and it is not scoped by area.** Two different shifts are both written as the bare text "9" - yellow (a single 09:00-18:00 shift) or light blue (split), per `ShiftCodeService`'s own javadoc. `ShiftCode` has no colour concept, and two rows can never share `(staffArea, code)` at once (V57's own unique index), so whichever `ShiftCode` the "other" colour of "9" means necessarily has a *different* `code` string that can't be known ahead of time. `RosterImportShiftColorMapping` remembers that resulting code string (not a `ShiftCode` id, so a later version bump - V57's own versioning - doesn't silently invalidate the mapping) keyed only by `(rawCode, fillColor)`, resolved once via `POST /roster/import/color-mappings`, which validates at that moment - not later, on every future resolution - that the chosen `ShiftCode`'s own shape (one interval or two) actually matches what the colour means. A "9" whose fill matches neither yellow nor light blue is a fatal parse issue, reported and never guessed at.

Area was in this key for one round of this feature's life (V78) and it was a mistake, corrected in V81 - worth stating plainly since the reasoning that produced it looks plausible on the way in. Real data shows Kitchen uses *both* colours for "9" in the same month, which proves department never *determines* which colour is meant - but that's a fact about the grid, not about what the memory needs to key on. Which actual `ShiftCode` row a resolved code string points to *is* resolved per area, separately, at read time (`ShiftCodeService#resolveActive(staffArea, code)`, fed the cell's own area, called after the colour mapping has already answered "which code text") - conflating that already-area-aware lookup with the colour-to-text mapping itself is what produced the wrong key. The hotel's own legend lists exactly two "9" entries, not one pair per department, and the accountant who set the codes up confirmed it directly: colour separates the two shifts everywhere, not per area. One mapping now resolves "9" for every department that uses that colour, the same way a name is mapped once and works for every month after.

**Comments are never read, including "do not move".** `RosterEntry#locked`'s own openapi.yaml description already calls itself "the system-recognized form of 'do not move' - already written by hand as a cell comment in the spreadsheet this module replaces," which looks like an invitation to wire the two together. Read against the hotel's own real file first: every "do not move" comment found sits on a *blank* (day-off) cell, not a coded one - and a day off has no `RosterEntry` for a lock to attach to at all (see that entity's own "absence of a row" convention). There is no reliable, general cell-to-entry mapping to be found here, so none is attempted, for any comment - not just the ones that would have been hard, since acting on some and silently dropping others is its own kind of guess.

**Names are never matched automatically, and existing entries are never overwritten.** A name is mapped once, by a person, and remembered by `(trimmed, whitespace-collapsed)` spelling against the account from then on - never inferred across months or fuzzy-matched. A cell whose `(employee, date)` already has a `RosterEntry` is always skipped and reported as a collision, never overwritten; resolving one, if the imported value should actually win, means clearing or editing the existing entry by hand and re-running the import. This also makes commit safe to retry after a lost response - anything already written the first time just shows up as a collision the second time.

**A staged upload lives in memory, keyed by an opaque id `commit` re-parses from.** Preview stores the raw file bytes (not the parsed/resolved result - resolution is re-derived fresh every time, from whatever's mapped *now*) in a plain in-memory map, swept opportunistically rather than on a `@Scheduled` job - this is a once-a-month, few-minutes-long admin task, not something worth a fourth periodic sweep, and this app's own "single hotel, single instance" premise (see this file's own opening line) is what makes in-memory state safe to reach for here at all.

**On-the-spot account creation doesn't fabricate an `EmployeePattern`.** "An employee can exist without login credentials" (see `UserService#create`) is what makes creating one mid-import cheap - name only, role `WAITER` (the safest default for an account nobody explicitly picked a role for), no email/password. The department a name's row sits under is used purely to resolve that name's own shift codes during this import; it is not persisted as an `EmployeePattern`, because that record also needs `workDaysPerWeek`/`weeklyDayOff`, which one month of attendance doesn't reliably establish - a manager sets that up deliberately, later, via the existing `/employee-patterns` screen, if this person turns out to have a standing weekly pattern worth generating from.

## Roster grid re-import (export -> edit -> re-import)

Distinct from the legacy Excel schedule import above - this is round-tripping the roster *grid* itself (already-committed `RosterEntry` rows) out to Excel, letting a manager edit it there, and syncing the changes back, rather than parsing the hotel's original hand-built file.

**The export embeds its own machine-readable ground truth in a hidden sheet, rather than re-deriving meaning from rendered cell styling on re-import.** A `VERY_HIDDEN` companion sheet carries employee ids, full historical `ShiftCode` field serialization (including `displayColor`), and a positional per-cell `shiftCodeId` pointer, cross-checked against the cell's own code text on re-import to catch silent staleness (the file was exported, the underlying `ShiftCode` changed since, and re-importing it would otherwise silently apply a stale mapping). This replaced an earlier design that tried to resolve a re-imported cell by matching its code text alone, which reintroduces exactly the kind of ambiguity `RosterImportShiftColorMapping` already exists to solve for the legacy import.

**Sync is a diff, keyed on `(employeeUserId, date)`, never a wholesale replace.** A re-import only ever adds, changes, or removes the specific cells that actually differ from what's currently in the database - a per-cell locked conflict is reported, not overridden. Staleness (the export is older than a since-changed entry) is recomputed fresh at `commit()`, never trusted from whatever `preview()` found - `preview()` and `commit()` can be arbitrarily far apart in time, and re-deriving from the database at the moment of the real write is what makes that gap safe.

## Working style

Investigate before changing. Several bugs in this project were "fixed" in the wrong place because behaviour was assumed rather than read.

When a decision is a judgment call — a data model, a permission boundary, anything touching money — state the options and the recommendation and wait, rather than choosing silently.

Do not touch the public site (`/public/**`, guest booking flow) unless the task is about it.
